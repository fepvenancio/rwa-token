Overview

Gated Token Stack

Tokens for fund shares and other real-world assets that only approved holders can hold. Each token keeps its own books and its emergency powers, and asks a separate, replaceable set of compliance rules before any balance changes.

20 contracts in contracts/ (interfaces and test mocks aside) Solidity 0.8.30, OpenZeppelin 5.6.1 ERC-20, ERC-7943, ERC-4626, ERC-7540 licence: UNLICENSED, proprietary

In one minute

An issuer of fund shares usually may sell only to approved investors, and must be able to act on an account: pause the token during an incident, hold back part of a balance, or move tokens out of an account. A plain ERC-20 token lets anyone send to anyone and has none of these powers. Here every token keeps the books and the powers, and hands every question about who may hold, send or receive to one outside contract, the hook. The hook asks a short list of small contracts, the rules, and the first rule that says no stops the movement. Rules can be replaced through governance without touching the token or its address.

The problem it solves

Real-world assets on a public chain need three things a plain token does not give. Who may hold them is decided by someone outside the chain (an identity provider, the issuer's onboarding). The issuer needs enforcement powers. And the policy changes over time: a new type of investor, a lockup, a limit on the number of investors in a fund.

The stack answers with a split. The token is a standard ERC-20 that refuses to move a balance unless its hook says yes. The hook is shared by every token of a deployment and keeps an ordered list of rules for each token. Each rule answers one question, such as "does the receiver hold a credential this token accepts" or "would this leave a balance below the minimum". Every token also implements ERC-7943, a standard interface for permissioned tokens, so outside tools can ask it canTransfer, canSend and canReceive before they send.

The life of a transfer

Every balance change takes the same path: a transfer, a mint, a burn, a forced transfer, an executed intent, a vault deposit or redemption. Here is a holder's plain transfer. One movement follows each step in full.

  1. The holder calls transfer(to, amount). Any entry point that changes a balance ends in the same internal function, _update, so no route skips the checks.
  2. The token describes the movement. It works out the kind (here TRANSFER) and builds the context the rules will see: the sender, the receiver, the amount, the account that called, and both balances before the move.
  3. The token runs its own checks. While the token is paused only forced movements pass. The amount must fit in the sender's unfrozen balance, the part the agent has not held back.
  4. The hook asks the token's rules in order. In the deployed lists: CredentialRule (the sender may leave, the receiver holds a credential the token accepts), MinPositionRule, HolderRestrictionRule (address freeze and lockup), SettlementWindowRule on the intent token (executed intents only), and FundHoldersRule (the fund's investor cap). The first rule that answers anything but TRANSFER_OK stops the movement, and the call reverts with PolicyGated_TransferRejected(reason).
  5. The balances move, then after_ runs. Rules that asked for it are told about the finished movement. FundHoldersRule is the one deployed rule that does: it tells Fund when the receiver starts holding this class or the sender stops.

Three design choices

  • The policy lives outside the token. The token's code has no opinion about who, where or when. A policy change is a new rule list on the hook, not a token upgrade, so the token keeps its address, balances and history.
  • Only reviewed code can be installed. Hooks, rules and token implementations are plain contracts (not proxies), and each must have its code hash recorded (attested) in PolicyRegistry by the security council. A token checks its hook, and each upgrade; the hook checks each rule; ProxyDeployer checks a new token's implementation; Fund checks its rule. The registry is asked at install time only, so withdrawing an attestation never changes a running token.
  • Authority waits, and the fast power can only stop. Changes go through a timelock with a delay. The guardian can pause at once and cancel queued changes, and cannot unpause, change policy or upgrade. A second timelock can unpause and remove the guardian, so the guardian cannot block its own removal.

Glossary

token
An ERC-20 contract that holds balances and asks its hook before every balance change. The stack has three templates: IntentToken, Gated4626Vault and Gated7540Vault.
proxy
A small contract that keeps a token's address and storage and runs the code of another contract, the implementation, for every call. Each token is a TokenProxy (OpenZeppelin's ERC1967Proxy). The upgrade function sits in the implementation (the UUPS pattern).
implementation
The shared code of one template, deployed once and used by every proxy of that template. Its constructor disables setup, so only a proxy can be set up.
hook
The contract a token asks before every balance change. Here it is ComplianceHook, one per deployment, holding an ordered rule list for each token.
rule
A small contract that answers one policy question about a movement with a reason code, such as TRANSFER_OK or RECEIVER_FROZEN. One instance serves every token whose list names it, and any setting it keeps is kept per token.
reason code
A bytes32 answer, the hash of a name like LOCKED. All of them are listed in contracts/interfaces/Errors.sol and on One movement.
kind
What sort of movement it is: TRANSFER (a holder's transfer), EXECUTED (a signed intent run by an executor), FORCED (an enforcement move by the agent), MINT or BURN. Rules decide differently per kind.
attested
The security council recorded a contract's code hash in PolicyRegistry as a reviewed HOOK, RULE or IMPLEMENTATION. It is checked when ProxyDeployer places a token, when a token installs a hook or is upgraded, when the hook installs a rule list, and when Fund installs its rule.
guardian
A multisig that can only stop things: pause the tokens and the executors with no delay, and cancel operations waiting in the main timelock. On the credential registry it can also block an address or switch off an attester.
timelock
A contract that holds admin powers and runs a queued operation only after a delay. The main timelock (GovernanceTimelock) administers everything. Outside itself, the recovery timelock can only unpause, remove the guardian, and undo the guardian's actions on the credential registry.
intent
A transfer a holder signs off-chain (an EIP-712 message): amount, receiver, deadline, a random single-use nonce, and optionally which executor may run it and what the holder is to receive in return.
executor
An account holding EXECUTOR_ROLE on the intent token, the only role that can run an intent. In the deployment it is held by IntentExecutor and DvPExecutor.
DvP
Delivery versus payment: the shares and the cash move in the same transaction, or neither moves. DvPExecutor does this from two signed legs.
fund
A Fund contract: a set of share-class tokens with one investor count and one cap across all of them.
class
One token registered in a fund. An investor who holds three classes counts once.
credential
The record an attester (an identity provider) keeps for an address in CredentialRegistry: who vouched for it, its qualification bits, its country, until when it is valid, and its standing.
frozen amount
The part of an account's balance that the agent holds back on a token (setFrozenTokens). The holder can move only the rest. It is not the same as an address freeze, which HolderRestrictionRule keeps and which stops the address from sending or receiving at all.
minimum position
A per-token minimum balance kept by MinPositionRule: no transfer, intent, mint or holder's burn may leave an account holding more than zero and less than the minimum. Forced moves, the burner's burns and exempt accounts are outside it. A minimum of 0 switches it off.
escrow
Tokens held by a contract on someone's behalf. Gated7540Vault holds shares waiting to be redeemed at its own address.

The contracts

One page per contract: what it is for, how it works, what it can do, and its tests.

Token

PolicyGatedERC20Upgradeable

The base every token extends: balances, roles, pause, frozen amounts, forced transfers and the call to the hook.

 IntentSettledUpgradeable

Adds transfers that a holder signs and an executor runs.

 IntentToken

The plain gated token: the base plus signed intents.

 Gated4626Vault

An ERC-4626 vault whose shares are a gated token.

 Gated7540Vault

An ERC-7540 vault: investors request, the fulfiller role fulfils, investors claim.

Policy

ComplianceHook

The one hook every token asks. An ordered rule list per token; the first rule to say no wins.

 BaseRule

The parent of every rule: default answers, and the guard that only a token's own hook may call after_.

 CredentialRule

Who may hold: reads the credential registry and applies the token's policy.

 MinPositionRule

No account left holding more than zero and less than the token's minimum.

 HolderRestrictionRule

Per-holder lockups and address freezes, set by the token's agent.

 SettlementWindowRule

Executed intents settle only inside the token's daily window.

 FundHoldersRule

Caps the number of distinct investors across a fund's classes.

Identity and fund

CredentialRegistry

One record per address: which attester vouched for it, what it qualifies for, until when.

 Fund

Lists a fund's share classes and counts distinct investors across them.

Governance and deployment

PolicyRegistry

The list of code hashes the security council has reviewed.

 GovernanceTimelock

The main timelock: holds the admin powers and runs changes after a delay.

 ProxyDeployer

Places each token at a predictable address and refuses to finish unless it came up as reviewed.

 TokenProxy

The proxy every token is: OpenZeppelin's ERC1967Proxy, created without setup data.

Settlement

IntentExecutor

Submits signed intents to a token, one at a time or as an all-or-nothing batch.

 DvPExecutor

Settles shares against cash in one transaction from two signed legs.
