Contracts / Deployment

TokenProxy

The contract every token actually is. It holds the token's balances and settings at a fixed address, and runs the token's code from a separate implementation contract. It is OpenZeppelin's standard proxy with a single setting changed.

contracts/deploy/TokenProxy.sol upgradeable proxy: OpenZeppelin ERC1967Proxy no admin of its own: upgrades need the token's UPGRADER_ROLE (the main timelock) not attested: its implementation is

In one minute

A proxy is a small contract with a permanent address that keeps the data and borrows its behaviour from another contract, the implementation. Holders, wallets and explorers only ever deal with the proxy's address. Upgrading a token means pointing its proxy at new code; the balances stay where they are. OpenZeppelin's proxy normally insists on being set up in the same step that creates it. TokenProxy relaxes that one rule, because the ProxyDeployer needs to create it first and set it up a moment later, still inside the same transaction, so that the token's address does not depend on its settings. No one can act in between.

How it works

The proxy has no token logic. On every call it runs the implementation's code with a delegatecall: the code executes as if it were the proxy's own, reading and writing the proxy's storage. The only thing the proxy itself stores is the implementation's address, in the standard ERC-1967 slot 0x3608…2bbc, which anyone can read with eth_getStorageAt.

  1. Create. ProxyDeployer creates the proxy with CREATE2 and the arguments (implementation, ""). The constructor stores the implementation in the ERC-1967 slot and, because the data is empty, calls nothing. The implementation must have code (ERC1967InvalidImplementation).
  2. Set up. ProxyDeployer calls the new proxy with the token's initialize call data. The proxy runs it through the implementation, and the token comes up with its admin, guardian, registry, hook and rule list.
  3. Check. ProxyDeployer reads the token back and reverts unless it came up as the call expected (ProxyDeployer).
  4. Serve. From then on every call to the token's address is forwarded to the current implementation.

What it can do

The proxy has a constructor and a forwarding fallback, nothing else. The upgrade function lives in the implementation, as UUPS prescribes.

The one override, and why it is safe here

OpenZeppelin's ERC1967Proxy reverts with ERC1967ProxyUninitialized when it is created with empty setup data, because a proxy left without its settings could be set up by whoever calls it first. Its documentation offers a hook to allow it, _unsafeAllowUninitialized(). TokenProxy overrides that hook to return true, and changes nothing else.

The reason is the token's address. CREATE2 derives the address from the deployer's address, a salt and the creation code with its arguments. ProxyDeployer uses the hash of the symbol as the salt and passes only the implementation as an argument. If the setup data went into the creation code too, the address would change with every admin, guardian, hook or rule in it. With empty data, the address depends on the symbol and the implementation alone, so it can be published and watched before the token exists.

It is safe because of how ProxyDeployer uses it:

  • No gap. ProxyDeployer creates the proxy and calls it with the setup data in the same function. Nothing else can run in between, so nobody can set the token up first.
  • No leftovers. If the setup or a later check fails, the whole call reverts and the proxy is never created.
  • No other proxy counts. A TokenProxy deployed any other way sits at a different address, because CREATE2 addresses include the deployer's own address, and none of ProxyDeployer's checks ran on it. It is not one of this system's tokens.
  • The code behind it cannot be set up directly. Each token implementation calls _disableInitializers() in its constructor, so the implementation contract itself can never be initialised; only proxies running it can.

Upgrades go through the token

The tokens use UUPS (the universal upgradeable proxy standard, ERC-1822): the upgrade function is part of the implementation's code, and the proxy has no admin and no upgrade function of its own. So the rules for upgrading sit with the token's other rules, in PolicyGatedERC20Upgradeable's _authorizeUpgrade.

  • Who. UPGRADER_ROLE is held by the main timelock and nobody else, so every upgrade is scheduled, waits out the delay, and can be cancelled by the guardian before it runs. The recovery timelock cannot upgrade.
  • What. Only an implementation the security council attested. Every deployment of an implementation has its own code hash, so each one needs its own attestation, even when built from identical source.
  • Which template. An attested vault implementation cannot be put under an intent token, or the reverse: each template reports its own templateId() and the token compares it with its own.
  • Ether. No token function accepts ether, and upgradeToAndCall, the one payable entry point, refuses it too: with empty data OpenZeppelin reverts with ERC1967NonPayable, and with data the delegated call is not payable.

Why it is built this way

  • OpenZeppelin's proxy, one documented override. Nothing about forwarding or storage layout is new code; the only change is the one OpenZeppelin provides a hook for.
  • A predictable address. The council can compute each token's address from the symbol and the implementation before deployment, and the deployment can be compared with it (Deployment and governance).
  • UUPS, so the proxy holds no power. The proxy has no admin to secure. Who may upgrade, and to what, is decided by the token's roles and the registry, the same way as everything else about the token.
  • The token's data never moves. An upgrade replaces code only. The token's balances, roles, frozen amounts and settings stay in the proxy's storage at the same address.
