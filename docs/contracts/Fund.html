Contracts / Fund

Fund

One fund, several share classes. Fund keeps what no single class can know: which tokens are its classes, how many distinct investors hold any of them, and which classes each investor holds.

contracts/fund/Fund.sol immutable, not a proxy owner: the main timelock after deployment not attested: the FundHoldersRule that points at it is

In one minute

A fund can issue several classes of shares, and here each class is its own token with its own balances. In the demo deployment the three classes are a token settled through signed intents, a vault and an asynchronous vault. A fund may be allowed only so many investors in total, counted across all its classes. No class token can count that alone, because it sees only its own holders.

Fund is the shared record. It knows the fund's classes, which of them each address holds, and how many distinct investors that makes. An investor in three classes counts once. It decides nothing itself: FundHoldersRule, a rule listed on every class, reads it to apply the cap and tells it when someone starts or stops holding a class.

How it works: one word per investor, one count for the fund

Classes are numbered from 1 in the order they were registered, and class n owns bit n - 1 of an account's class mask. Each account's state is one storage word: the class bits at the bottom and an "exempt" flag at the top. The fund's installed rule, the investor count and the cap share another word.

  1. An investor is an account that holds at least one class and is not exempt. It counts once, however many classes it holds.
  2. A class never counts itself. Gated7540Vault holds the shares of pending redemptions at its own address. join ignores a class token joining itself, so the escrow is never recorded and needs no exemption.
  3. The count moves only at the edges. It rises when an account gets its first class bit while not exempt, and falls when a non-exempt account loses its last one. A second class, or an extra unit of one already held, writes nothing to the count.
  4. The shared word. The installed rule, the count and the cap sit in one storage slot, so the rule reads all three at once, and the first count write is never a write to an empty slot.

Registering a class

The owner calls registerClass(token). The checks run in this order:

  1. The token is not the zero address (Fund_ZeroAddress) and is not already a class (Fund_AlreadyRegistered).
  2. The fund has fewer than MAX_CLASSES, 32, classes (Fund_TooManyClasses). The mask has a bit for each.
  3. A rule is installed (Fund_RuleNotSet).
  4. The token reports ERC-165 support for IPolicyGated, the interface of every gated token (Fund_NotPolicyGated).
  5. The token's current hook lists the installed rule for it (Fund_RuleNotListed). A token with no hook fails here too: the call to its hook reverts.
  6. The token's total supply is zero (Fund_ClassHasSupply). A class with holders the fund never saw would start with a wrong count.

Registration is permanent; there is no function to remove a class. Until a token is registered, FundHoldersRule rejects every movement on it with NOT_FUND_CLASS, so no balance can exist before the fund records it. The calls to the token and its hook are read-only.

In the deployment, Activate installs the rule and sets the cap (the fundHolderCap parameter, which has no default), then registers the intent token, the 4626 vault and the 7540 vault one after another, as classes 1, 2 and 3, and only then hands ownership of the fund to the main timelock.

Who may change the record

The fund's state is shared by every class, so a token that merely names itself in a movement must not reach it. Two gates stand in the way:

  • Only the installed rule. join and leave revert for any other caller (Fund_OnlyRule). The rule in turn accepts after_ only from the hook the token currently has installed.
  • Only a registered class. join and leave revert for a token that is not a class (Fund_NotAClass). A fake token with its own fake hook can get past the rule's hook check, and is stopped here.

The owner's setExempt is the one other path that moves the count, and only by one, for an account that holds a class. The owner cannot set a class mask or the count directly.

The cap and the exemptions

  • The cap. setHolderCap stores it and leaves the count alone. Lowering it below the current count does not remove anyone: existing investors keep their classes, can trade among themselves and can leave, and while the count is above the cap the rule admits nobody new. A cap of 0 admits no new investor. The count and the cap are 48-bit numbers.
  • Exemptions. An exempt account, such as a treasury, never counts and never triggers the cap. Its class bits are still recorded, so if the owner ends the exemption while it holds a class, it enters the count at once, and the reverse when an exemption starts. Exempting an account that holds nothing changes only the flag.
  • Not checked by the fund. Neither change looks at the classes or the rule. Both are owner calls, which after deployment means main-timelock operations with their delay.

Changing the rule

setRule(newRule) takes effect at once: from then on only newRule may call join and leave. The count and the masks stay where they are, and the new rule starts from them. But each class's hook lists its rules by address. A class whose list still names the old rule sends it every movement, and the old rule, seeing from admission that it is not the installed rule, rejects every movement of that class with NOT_FUND_CLASS, forced transfers and burns included. The pre-flight calls give the same answer and the fund's state does not change, but the class is closed until its list names the new rule.

So the change goes through the main timelock as one batch: fund.setRule(newRule) and, for every registered class, hook.setRules(class, list) with the old rule replaced by the new one in the class's list. A second rule instance for the same fund has the same code hash as the first, because the fund's address is its only immutable, so it is already attested.

The monitor: isClassIntact and firstBrokenClass

The cap lives in the fund, but it applies to a class only while that class's rule list in the hook names the fund's installed rule. The hook accepts any list of attested rules, so it cannot know when a list loses the fund's rule. The fund can check.

ViewAnswer
isClassIntact(token)True when the token is a registered class and its current hook's rules(token) lists the installed rule. False otherwise, including when the token cannot name its hook or the hook cannot list its rules.
firstBrokenClass()The first registered class, in registration order, that is not intact; the zero address when every class is. One call, at most 32 classes.

Neither view reverts on the thing it watches. They report three situations and prevent none of them: the fund's rule dropped from a class's list (the class runs uncapped and the fund's count goes stale), the fund's rule replaced while a list still names the old one (the class fails closed with NOT_FUND_CLASS), and a class's hook swapped for one that does not list the rule. The post-deployment check asserts that firstBrokenClass() is the zero address.

Why it is built this way

  • State in the fund, policy in the rule. The fund only records. The rule decides. Replacing the rule keeps the count and the masks, because they never lived in the rule.
  • One word per account, one for the fund. A class mask and the exempt flag fit one storage word, and the rule, the count and the cap share another, so the rule's usual question costs one call (admission).
  • Supply must be zero at registration. The fund cannot discover holders it never saw, so a class joins before anyone holds it, and the count is right from the first unit.
  • Balances are not added up. positionsOf returns each class's balance separately, because units of different classes are not comparable.
  • Owned, not administered by a fixed address. Like ProxyDeployer, the fund is Ownable: the deployer configures it during deployment and then hands it to the main timelock. A fixed admin would have forced a timelock operation, and its delay, onto every first deployment.
  • Not attested itself. The council attests FundHoldersRule, whose code hash covers the fund's address as an immutable but not the fund's code. The council reads the fund's code and owner before attesting the rule.
  • Tested as a whole. An invariant test drives random holder and enforcement actions across the three templates and checks that every class bit matches a positive balance, that the count is the number of non-exempt investors, and that no class and no outside account is ever recorded.
