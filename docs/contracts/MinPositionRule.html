Contracts / Policy

MinPositionRule

A minimum holding per token. After a movement, every account it judges holds either nothing or at least the minimum, so no tiny leftover balances (dust) are created.

contracts/hooks/rules/MinPositionRule.sol immutable, not a proxy set per token by the token's DEFAULT_ADMIN_ROLE attested as RULE

In one minute

Funds often set a minimum investment. This rule enforces one on the token: if the minimum is 1,000 units, nobody can end a transfer, a subscription or a redemption holding 1 to 999 units. Selling everything is fine; keeping a little is not. It also matters for the investor cap: a tiny balance would count as a whole investor, so blocking dust stops anyone from taking a place under the cap with one unit. The token's administrator sets the minimum, and 0 switches the rule off. Enforcement actions (the agent's forced transfers and the burner's burns) are not held to it.

How a position is judged

The rule looks at the balance each side will have after the move. It reads both balances before the move from the context the token built (extra) and adds or subtracts the amount, so it never calls back into the token for a balance.

What it checks for each kind of movement

With a minimum above 0, a non-zero amount, and two different accounts:

KindReceiverSender
TRANSFERends at the minimum or more, unless exemptkeeps 0, or the minimum or more, unless exempt
EXECUTEDthe same as a transferthe same as a transfer
FORCEDnot judgednot judged (an enforcement mint has no sender)
MINTends at the minimum or more, unless exemptnone: a mint has no sender
BURNnone: a burn has no receiverkeeps 0, or the minimum or more, unless exempt or the operator holds the token's BURNER_ROLE

The refusal is always BELOW_MIN_POSITION, and the token reverts with PolicyGated_TransferRejected(BELOW_MIN_POSITION). A holder's own burn, such as a vault redemption, is judged on what it leaves behind; a burn by the token's burner is an enforcement action and may leave any remainder.

What is not judged

  • Nothing to judge. A minimum of 0 (the rule is off for the token), an amount of 0, and a move from an account to itself all pass. Nothing changes hands, so no new dust appears.
  • Enforcement. FORCED passes on both sides, the enforcement mint included, and so does a burn whose operator holds the token's BURNER_ROLE on the sender side. The rule asks the token for that role only when a burn would leave a remainder below the minimum.
  • The token itself. The token's own address is always exempt. On Gated7540Vault the token is also the escrow that holds the shares of pending redemptions.
  • Listed accounts. The token's admin can exempt an account with setExempt(token, account, true). An exempt account is not judged on its own side; the other side of the same movement still is. A listing on one token does not carry over to another.

The rule asks the token at call time whether the caller holds DEFAULT_ADMIN_ROLE, through a read-only call. During deployment the deploying account is still each token's admin and sets each minimum from the parameters intentMinPosition, fundMinPosition and asyncFundMinPosition, all 0 by default, so the rule starts switched off. After the hand-over the main timelock is the admin, and a change is a governance operation with its delay.

Edge cases

  • Raising the minimum. Existing balances are not touched. A holder left below a raised minimum cannot send part of it, but can send all of it to a receiver that then holds at least the minimum, redeem all of it, or receive enough to reach the minimum. A top-up that still leaves it below is refused.
  • Small amounts to existing holders. A receiver that already holds at least the minimum can receive any amount, even 1 unit, as long as the sender keeps 0 or at least the minimum.
  • An amount above the balance. The token never offers such a movement to the hook on a write, but its canTransfer asks with it. The rule answers without reverting: the sender side is only computed when the sender holds more than the amount.
  • It never reverts on arithmetic. The receiver test is written as "the amount is below the minimum, and the balance is below the minimum minus the amount", which cannot overflow, and the sender's remainder is only computed when it is positive. A Halmos symbolic test proves that for any minimum, balances, amount and kind it answers without reverting.
  • Vault limits. The vaults' maxDeposit and maxMint test a mint of a very large amount (type(uint128).max), which is above any minimum up to that size, so a minimum does not show up there as a block. A deposit too small for the minimum passes that check and is refused when the shares are minted. On Gated7540Vault a claim that would leave the receiver below the minimum is refused and the claimable amount stays; the agent's recoverClaimable delivers it as an enforcement mint, which is exempt.

Why it is built this way

  • No dust, no cheap investor slots. The fund caps its number of investors (FundHoldersRule), and a one-unit balance counts as an investor. With a minimum set, a movement this rule judges cannot create such a position. The deployed lists put this rule second, right after the credential check, so the rules after it see real positions. Forced transfers, exempt accounts and burns by the burner can still leave dust.
  • No call back into the token for balances. The token puts the balances before the move in the context, the same way for the write and for every pre-flight, so the usual path makes no call to the token at all. The token is asked only for a role, and only when a burn would leave dust.
  • One instance for every token. The minimum and the exemptions are stored per token and authorised by that token's own admin, so the same attested contract serves every token in the deployment.
  • No account-level opinion. ERC-7943 keeps quantitative rules out of canSend and canReceive, so this rule leaves them to check.
