Contracts / Governance

PolicyRegistry

The list of reviewed code. For each code hash the security council has reviewed, it records what that code may be installed as: a hook, a rule or a token implementation. Every place that installs one of those asks it first.

contracts/governance/PolicyRegistry.sol immutable, not a proxy admin: the main timelock; attester: the security council not attested: it is the list itself

In one minute

Every deployed contract has a code hash: a fingerprint of its code. Change one byte and the fingerprint changes. The security council reads a piece of code, then writes its fingerprint here together with what it is for. When a token is created, upgraded, or given a new hook, or when a token's list of rules changes, the contract doing the install asks the registry one question: is this exact code on the list, for this purpose? If not, the install fails. The registry is asked only at that moment. Taking a fingerprint off the list later does not switch off anything already running; governance replaces the component as a separate step.

How it works

The registry stores one kind per code hash: HOOK, RULE or IMPLEMENTATION, or NONE when nothing is stored. isAttested(target, kind) reads the code hash of the address it is given and compares the stored kind with the kind asked for. Six places in the system ask it, two for each kind.

The deployment passes the main timelock and the council, so the registry is under governance from its first block. Attesting and revoking wait for no timelock: they are the council's own actions.

What a code hash covers

A code hash is the hash of a contract's runtime code, and that code includes the values of its immutable variables. It does not include storage. Several things follow from that, and each shapes how the system is deployed.

  • Identical code shares one attestation. Two contracts with the same runtime code have the same hash, so attesting one attests both (the registry test test_WhenAnotherContractHasTheSameCode_ItReturnsTrue).
  • The shared hook. ComplianceHook's only immutable is its registry, so one attestation covers the one hook every token uses, and any other hook built on the same registry carries the same hash. A token refuses a hook that names another registry. The rule list each token runs lives in the hook's storage, which the hash does not cover, so ProxyDeployer and the post-deployment check compare the exact hook instance and each token's list.
  • Each implementation needs its own attestation. OpenZeppelin's UUPS code stores the implementation's own address in an immutable, so every deployment of a token implementation has a different hash, even from identical source.
  • Rules that point at another contract. CredentialRule holds its credential registry's address as an immutable, and FundHoldersRule holds its fund's. The hash covers those addresses, not the code at them, so the council reads the contract each one points at before it attests the rule.

Asked when code is installed, not on every movement

No token asks the registry when tokens move. The registry is read when a hook, a rule list, a fund rule or an implementation is installed, and never again for that install. revoke therefore changes nothing that is already running. It stops the same code from being installed anywhere afterwards.

If a revoke reached running tokens, it would have to do one of two things to each token that runs the revoked code: skip that check, so a rule silently stops applying, or fail every movement. Asking only at install time leaves that decision to governance. The guardian can pause the affected tokens at once, and the main timelock then replaces the component, which waits out its delay. Pause does not stop a forced transfer, which still runs the hook and its rules.

Why hooks and rules must be plain contracts

The registry compares the code at an address, so what it vouches for must be all of that component's behaviour.

  • No proxies. A proxy's code hash is the hash of the small forwarding contract, not of the code it forwards to. Attesting a proxy would vouch for whatever implementation it points at later. Hooks and rules are therefore ordinary contracts: changing one means deploying new code, having it attested, and installing it through governance.
  • No authority in storage. Anyone can deploy a copy of attested code and give the copy different storage, and the copy carries the same attestation. So whatever matters for security has to be fixed in the code or its immutables. The hook's registry and a rule's credential registry or fund are immutables. Rules keep no owner or role of their own: they ask the token's roles at the moment of the call (IAccessControl(token).hasRole), and the post-deployment check asserts that no rule exposes hasRole or owner.
  • Token implementations are the one kind behind a proxy. Their gate is the upgrade itself, and the template check keeps a token on its own template.

Why it is built this way

  • One immutable list per deployment. The registry is not a proxy and has no setter beyond its roles, so the list of reviewed code cannot be swapped by an upgrade. Every token, the hook, the fund and the deployer take its address when they are set up, and tokens and the deployer check that they agree on it.
  • By code, not by address. An attestation follows the bytes the council read, immutables included. The council publishes where the review is through uri, and the Attested and AttestationRevoked events record who did what.
  • One kind per hash. A hash cannot be a hook and a rule at once. Changing its kind takes a revoke first, then a new attestation, so the change is visible in the events.
  • Empty hashes are refused. An address with no code has a code hash of zero or the hash of empty code. attest refuses both, so an empty address can never pass a gate.
  • Separate duties. The council attests and revokes. The main timelock, with its delay, decides who sits on the council. Neither touches tokens directly through the registry.
