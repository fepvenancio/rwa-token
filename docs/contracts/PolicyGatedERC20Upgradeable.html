Contracts / Token

PolicyGatedERC20Upgradeable

The base every token in the stack is built on. It keeps the balances, the roles and the enforcement tools, and it sends every balance movement through one path that asks the compliance hook before anything moves.

contracts/base/PolicyGatedERC20Upgradeable.sol abstract: runs inside each token, behind its proxy admin: the main timelock on each token attested as part of each template implementation

In one minute

The intent token and both vaults share this code. It does the bookkeeping of an ordinary ERC-20 token, plus what a regulated issuer needs: create and destroy tokens, move tokens without the holder's consent (a forced transfer), freeze part of a holder's balance, and pause the token in an emergency.

It never decides who may hold the token, where or when. For every movement it asks a separate contract, the policy hook, which runs a list of small checks called rules (identity, lockups, settlement hours, the fund's investor cap). The hook and its rules can be replaced through governance without touching the token. Changing this base itself takes an upgrade to code the security council has reviewed and recorded in the registry (code that is attested).

How every movement is decided

A transfer, a mint, a burn, a forced transfer and a signed intent all end in the same internal function, _update. It labels the movement with one of five kinds, builds a description of it for the hook (the context), runs the token's own mechanical checks, asks the hook, and only then moves the balances.

  1. The kind. forcedTransfer and executeTransfer announce their kind with _moveAs, which writes it (and, for an intent, its ref and deadline) into transient storage, storage that lives only for the current transaction. _update reads the slots and clears them, so a later movement in the same transaction is classified afresh. With nothing announced, the kind follows from the addresses: from zero is MINT, to zero is BURN, anything else is TRANSFER. Templates use the same tools for their own enforcement moves: the 7540 vault announces FORCED with _moveAs and _mintAs when it recovers a stranded request.
  2. The context. The token builds it; no caller can supply one. The operator is whoever called the token: the holder, a spender, the agent, the minter, the burner or the executor. extra carries the balances of both sides before the move, so rules never have to call back into the token for them.
  3. The hook is read once. The hook that approves a movement is the hook that later sees afterTransfer, even if the hook pointer changed in between.
  4. Pause. While the token is paused, every kind except FORCED is refused, mints and burns included.
  5. The unfrozen bound. A sender can move only the part of its balance that is not frozen. A forced transfer, and a burn whose operator holds BURNER_ROLE, may take frozen tokens, but never more than the balance. The token names the cause: an amount within the balance but above the unfrozen part reverts with ERC7943InsufficientUnfrozenBalance(account, amount, unfrozen); an amount above the balance reverts with ERC20InsufficientBalance(account, balance, amount). Only this check uses those errors. A hook that returns the code INSUFFICIENT_UNFROZEN by itself is a policy rejection like any other. burn and forcedTransfer check the balance first, before _update runs, so for them an amount above the balance reverts with ERC20InsufficientBalance before the pause or the hook is asked.
  6. The hook decides. beforeTransfer is a read-only call that returns TRANSFER_OK or a reason code. Anything else reverts with PolicyGated_TransferRejected(reason). A token with no hook would answer NO_HOOK, but the initialiser and setPolicyHook both refuse a zero hook.
  7. The balances move with OpenZeppelin's ERC-20 logic, which emits Transfer.
  8. After the move. If the hook asks for it (wantsAfter()), afterTransfer runs with the same context; the fund rule uses it to keep the investor count. It is still inside the reentrancy guard, so a hook or rule that tries to start another movement on the token reverts.

Roles and the guardian

Access is OpenZeppelin AccessControl. No role has an admin of its own, so DEFAULT_ADMIN_ROLE grants and revokes every role. After deployment that is the main timelock, a contract that runs an approved call only after a waiting period (seven days by default in the deployment) during which it can be cancelled.

The guardian can only stop things. It pauses the token at once, and on the main timelock it holds CANCELLER_ROLE, so it can cancel any pending governance operation. It cannot unpause, change the hook, grant a role or upgrade.

Why a second timelock. A guardian that can cancel governance operations could also cancel its own removal, or an unpause it disagrees with. The recovery timelock closes that gap. It has the same delay, the governance multisig proposes and executes on it, it has no cancellers, and the guardian holds nothing on it. On every token it holds RECOVERY_ROLE, which allows exactly unpause() and revokeRole(GUARDIAN_ROLE, account). Any other call from it fails with the usual access error.

Frozen amounts

The agent can freeze an amount of a holder's tokens with setFrozenTokens. The token stores one number per account, not a list of specific tokens. The unfrozen balance is the balance minus the frozen amount, or zero when the frozen amount is the larger. Following ERC-7943, the frozen amount may be set above the balance. It changes only when the agent sets it, or when an enforcement action takes frozen tokens; a holder receiving or sending tokens leaves it as it is.

  • Holders, spenders and executors move at most the unfrozen balance, whatever the kind: a transfer, an executed intent, and a vault redemption (a holder's burn) alike. A holder's own burn counts frozen tokens against it.
  • Enforcement (forcedTransfer, and burn by a BURNER_ROLE holder) can take up to the whole balance. Before moving, it lowers the frozen amount by the part of the amount the unfrozen balance does not cover. With a balance of 10 and a frozen amount of 100, forcing 10 leaves a frozen amount of 90. When the unfrozen balance covers the amount, the frozen amount stays as it is and no Frozen event is emitted.
  • Address freeze is a different tool. This is a freeze of an amount on one token, in the token. Blocking an address from sending or receiving at all is a setting of the holder restriction rule, in the hook.

Asking before moving

Wallets, exchanges and the vaults ask the token whether a movement would pass before sending it. canTransferWithReason and canTransfer run the movement path above without moving anything. They simulate a movement driven by from itself (the operator is from, or the caller for a mint), so a pre-flight of a burn is a holder's burn. They do not model forcedTransfer, which ignores the pause and may take frozen tokens.

The two differ on one case, because ERC-7943 says canTransfer must not fail on a plain balance check but must fail while frozen tokens are in the way.

A sender that holds BURNER_ROLE, asking about its own burn, is not held back by frozen tokens, so above its balance it reads like the last row. To learn whether a movement will succeed, use canTransferWithReason.

canSend(account) and canReceive(account) ask a different question: may this account send, or receive, this token at all? They are false while the token is paused or has no hook. Otherwise the hook asks each rule's account-level answer for this token and stops at the first refusal. They take no amount and no counterparty, so the minimum position, the settlement window and the fund's investor cap never show in them; the minimum position and the investor cap appear only in the movement pre-flights, and the settlement window only in canExecute.

During a pause

  • Refused: every movement whose kind is not FORCED. That covers transfers, mints, burns (the burner's too), executed intents, and vault deposits and redemptions. canSend and canReceive answer false.
  • Still possible: forcedTransfer and the 7540 vault's own FORCED recoveries, setFrozenTokens, approve and permit, cancelling a signed intent, role changes, replacing the hook and upgrades. The rules still run on a forced transfer, so the receiver must still be eligible.
  • Lifting it takes a timelock operation: the main timelock, or the recovery timelock if the guardian keeps cancelling. There is no automatic expiry.

Replacing the hook

setPolicyHook(newHook) is a timelock call. The new hook must not be the zero address (PolicyGated_ZeroAddress), its code hash must be attested as HOOK in the token's registry (PolicyGated_NotAttested), and it must name the same registry (PolicyGated_HookRegistryMismatch(hookRegistry, tokenRegistry)), because a hook shared by several tokens checks their rules against its own registry.

The hook keeps the rule list of each token itself, and the swap does not copy it. As the token's admin, the timelock sets this token's list on the new hook with setRules. Until it does, the new hook refuses every movement of the token with NO_RULES.

When the token is first set up, its initialiser installs the hook with the same checks and then calls hook.setRules(token, rules) itself, so the token is live with its policy from the first block. See ComplianceHook.

Upgrades

Each token is a proxy: a small contract that holds the balances and forwards every call to shared code, its implementation. An upgrade points the proxy at new code (OpenZeppelin UUPS, upgradeToAndCall). The base checks three things, in this order:

  1. The caller holds UPGRADER_ROLE, which the deployment gives to the main timelock only.
  2. The new implementation's code hash is attested as IMPLEMENTATION (PolicyGated_NotAttested(impl, IMPLEMENTATION)). Every implementation deployment has its own code hash, so each one needs its own attestation.
  3. It reports the same templateId() as the current one (Templated_WrongTemplate(impl, expected, actual)). The id is keccak256 of the template's name with no version, so a bug-fix release of the same template passes, while an intent token cannot be moved onto a vault's code even if that code is attested. Code with no templateId() at all is refused.

Standards it speaks

  • ERC-7943 (uRWA, the fungible interface): forcedTransfer, setFrozenTokens, getFrozenTokens, canSend, canReceive, canTransfer, with the events ForcedTransfer and Frozen and the error ERC7943InsufficientUnfrozenBalance. The interface also declares the optional errors ERC7943CannotSend, ERC7943CannotReceive and ERC7943CannotTransfer; the token does not use them and rejects with PolicyGated_TransferRejected(reason), which carries the reason.
  • ERC-165: supportsInterface answers true for IPolicyGated, IERC7943Fungible (0x3edbb4c4), IERC20, IERC20Permit, IAccessControl and IERC165. The intent token adds ITransferIntent.
  • ERC-2612 permit: approval by signature. Its EIP-712 domain is the token name, version "1", the chain and the token address, the same domain as signed intents.
  • Multicall: multicall(bytes[]) runs each call on the token itself, so the caller stays the sender and its roles apply to every call. A minter can mint to several accounts, or an agent can set a frozen amount and force a transfer, in one transaction. If one call fails, all are undone. Each movement inside still goes through _update on its own, and an announced kind is cleared before the next call.

Why it is built this way

  • One path, shared with the pre-flights. The write and the pre-flight answers build the context and run the checks with the same functions (_context, _check), so they cannot drift apart. The one difference is the ERC-7943 balance case above.
  • No policy in the base. The base checks only mechanical things: pause, the frozen bound, roles, attestations. Every question of who, where or when is a rule in the hook, so policy can change without upgrading the token.
  • Balances travel in the context. Rules read both balances from extra and work out the balances after the move from amount. They never need to call back into the token for them, and the reentrancy guard on _update makes any attempt to start a second movement fail.
  • Kinds in transient storage. A forced transfer and an intent need a kind the addresses cannot show. Writing it to transient slots that _update clears keeps one _update for everything, and a revert rolls the slots back.
  • Installed checks, not running checks. The registry is asked when a hook or implementation is installed. A later withdrawal of an attestation does not change a running token: governance removes the component and the guardian can pause meanwhile, so a revocation never silently drops a check or blocks every transfer.
  • The registry is fixed at setup. The initialiser refuses a zero admin, guardian or registry (PolicyGated_ZeroAddress), and there is no setter for the registry.
  • Reason codes cannot default to yes. Each code is the keccak256 of its name, so TRANSFER_OK is not zero, and a hook or rule that forgets to set its answer refuses instead of approving.
  • Namespaced storage. The registry, the hook pointer and the frozen amounts live in one ERC-7201 namespace (gated.storage.PolicyGatedERC20), apart from the OpenZeppelin parents and the templates, which keeps upgrades safe.
