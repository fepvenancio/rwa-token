Contracts / Token

PolicyGatedERC20Upgradeable

The base every token in the stack is built on. It keeps the balances, the roles and the enforcement tools, and it sends every balance movement through one internal function that asks the policy hook before anything moves.

contracts/base/PolicyGatedERC20Upgradeable.sol abstract: runs inside each token, behind its proxy admin: the main timelock on each token, after hand-over attested as part of each template implementation

In one minute

GatedToken, IntentToken and both vaults share this code. It does the bookkeeping of an ordinary ERC-20 token, plus what a regulated issuer needs: create and destroy tokens, move tokens without the holder's consent (a forced transfer), freeze part of a holder's balance, and pause the token in an emergency.

It does not decide who may hold the token, where or when. For every movement it asks a separate contract, the policy hook, which runs a list of small checks called rules (identity, lockups, settlement hours, a fund's investor cap). The hook and its rules can be changed through governance without touching the token. Changing this base takes an upgrade to code the security council has reviewed and recorded in the registry (code that is attested).

How every movement is decided

A transfer, a mint, a burn, a forced transfer and a signed intent all end in one internal function, _move. OpenZeppelin's ERC-20 code reaches it through _update, and the enforcement routes reach it through _moveAs and _mintAs. Each movement carries one of five kinds. _move builds a description of the movement for the hook (the context), runs the token's own mechanical checks, asks the hook, and only then moves the balances.

  1. The route and the kind. transfer, transferFrom, mint and burn use OpenZeppelin's _transfer, _mint and _burn, which call _update. The base overrides _update to call _move with a kind worked out from the addresses: from zero is MINT, to zero is BURN, anything else is TRANSFER. A kind the addresses cannot show is announced. forcedTransfer and executeTransfer call _moveAs, which passes the kind, and for an intent its ref and deadline, as arguments, and refuses a zero from or to (ERC20InvalidSender, ERC20InvalidReceiver). A forced transfer within the balance can reach that refusal, with a zero receiver, or with a zero from and a zero amount. An intent with a zero to or from is stopped before it, by ZERO_RECEIVER or BAD_SIGNATURE. _mintAs(to, amount, kind) passes the kind for a mint and refuses a zero to: the 7540 vault's recoverClaimable uses it for an enforcement mint, FORCED with a zero from. Nothing is stored between calls, so each movement in a transaction gets its kind from its own route. _update does not see forced or executed movements, so a template that had to act on every movement would extend _move.
  2. Enforcement releases first. forcedTransfer and burn call _releaseFrozen before the path starts. It reverts with ERC20InsufficientBalance for an amount above the balance, so for these two functions that error comes before the pause or the hook is asked. See Frozen amounts.
  3. The context. The token builds it, and no caller can supply one. See What the hook is told.
  4. The hook is read once into a local variable. The hook that approves a movement is the hook that sees its afterTransfer.
  5. Pause. While the token is paused, every kind except FORCED is refused, mints and burns included.
  6. The unfrozen bound. The amount must fit in what from can move: the unfrozen balance, or the whole balance for a forced movement and for a burn whose operator holds BURNER_ROLE. A mint has no sender, so this step does not apply to it. The write names the cause: an amount within the balance but above the unfrozen part reverts with ERC7943InsufficientUnfrozenBalance(account, amount, unfrozen), and an amount above the balance with ERC20InsufficientBalance(sender, balance, needed). A hook that returns the code INSUFFICIENT_UNFROZEN with no shortfall behind it is a policy rejection like any other (test_WhenTheHookItselfReturnsInsufficientUnfrozen_ItIsAPolicyRejection).
  7. The hook decides. beforeTransfer(ctx) is a read-only call that returns TRANSFER_OK or a reason code. Anything else reverts with PolicyGated_TransferRejected(reason). A token with no hook would answer NO_HOOK, but the initialiser and setPolicyHook both refuse a zero hook, so no function of the base leaves a token in that state.
  8. The balances move with OpenZeppelin's ERC-20 logic, which emits Transfer.
  9. After the move. If wantsAfter() is true, afterTransfer(ctx) runs with the same context; the fund rule uses it to keep the investor count. It is still inside the reentrancy guard, so a hook or rule that tries to start another movement on the token reverts with ReentrancyGuardReentrantCall (test_WhenARuleReentersTheToken_TheTransferReverts).

Frozen amounts

The agent can freeze an amount of a holder's tokens with setFrozenTokens. The token stores one number per account, not a list of specific tokens. The unfrozen balance is the balance minus the frozen amount, or zero when the frozen amount is the larger. Following ERC-7943, the frozen amount may be set above the balance, and on an account that holds nothing (test_WhenAnAccountHoldsNothing_ItCanStillBeFrozen). It changes in two ways: the agent sets it, or an enforcement action takes frozen tokens. A holder receiving or sending tokens leaves it as it is.

  • Holders, spenders and executors move at most the unfrozen balance, whatever the kind: a transfer, an executed intent, and a vault redemption (a holder's burn) alike. A BURNER_ROLE holder's plain transfer counts frozen tokens too; the exemption is for a burn.
  • Enforcement (forcedTransfer, and a burn whose operator holds BURNER_ROLE) can take up to the whole balance, and never more. Before moving, burn and forcedTransfer lower the frozen amount by the part of the amount the unfrozen balance does not cover. With a balance of 10 and a frozen amount of 100, forcing 10 leaves a frozen amount of 90 (test_WhenFrozenExceedsTheBalance_ForcedTakesOnlyWhatMovesFromIt). When the unfrozen balance covers the amount, the frozen amount stays as it is and no Frozen event is emitted (test_WhenTheAmountIsWithinTheUnfrozenBalance_NothingIsReleased).
  • Tokens received later are covered by a frozen amount above the balance until the balance passes it, because the unfrozen balance is worked out at each movement.
  • An address freeze is a different tool. This is a freeze of an amount on one token, kept in the token. Blocking an address from sending or receiving at all is a setting of HolderRestrictionRule, in the hook. A frozen amount does not stop an account receiving, and canSend does not read it.

Asking before moving

Wallets, exchanges and the vaults ask the token whether a movement would pass before sending it. canTransferWithReason and canTransfer run the checks of the movement path without moving anything. They simulate a movement driven by from itself: the operator is from, or the caller for a mint, whoever asks (test_WhenCalledByAThirdParty_ItSimulatesATransferByFrom). A zero from reads as a mint and a zero to as a holder's burn.

The two differ in one case, because ERC-7943 says canTransfer must not fail on a plain balance check and must fail when frozen tokens are in the way.

So to learn whether a movement will succeed, use canTransferWithReason. It is the same check the write runs, apart from the error it would turn into: it answers INSUFFICIENT_UNFROZEN where the write names one of the two balance errors. canTransfer is that check with the ERC-7943 exception: a shortfall counts only while a frozen amount is in the way of a holder. While part of the balance is frozen, an amount above the balance reads false; the standard does not say which clause wins there, and this is what the reference implementation published with ERC-7943 does.

canSend(account) and canReceive(account) ask a different question: may this account send, or receive, this token at all? They are false while the token is paused or has no hook. Otherwise they return the hook's checkSend or checkReceive, which asks each rule's account-level answer and stops at the first refusal. They take no amount and no counterparty, and ERC-7943 keeps quantitative rules out of them. So:

  • A new investor at a full fund reads canReceive true, and the movement is refused with MAX_HOLDERS. The minimum position and the settlement window are not in them either.
  • A locked or address-frozen holder reads canSend false, although forcedTransfer still passes the rules for both.
  • A holder whose whole balance is frozen with setFrozenTokens still reads canSend true when the rules accept it, and canTransfer false for any amount above zero.

ERC-7943 also has canTransfer perform the canSend and canReceive checks. Here canTransfer runs the movement path instead. For a plain transfer through the shipped rules it is not true while either account answer is false; testFuzz_CanTransferNeverExceedsTheAccountQuestions fuzzes that, in that one direction.

Roles and the guardian

Access is OpenZeppelin AccessControl. No role has an admin of its own, so DEFAULT_ADMIN_ROLE grants and revokes every role. After hand-over that is the main timelock, a contract that runs an approved call after a waiting period (24 hours by default in the deployment, with a floor of 1 hour in GovernanceTimelock) during which it can be cancelled.

The guardian can only stop things. It pauses the token at once, and on the main timelock it holds CANCELLER_ROLE, so it can cancel any pending governance operation. It cannot unpause, change the hook, grant a role or upgrade.

Why a second timelock. A guardian that can cancel governance operations could also cancel its own removal, or an unpause it disagrees with. The recovery timelock closes that gap. It has the same delay, the governance multisig proposes and executes on it, it has no cancellers, and the guardian holds nothing on it. On a token, revokeRole lets a RECOVERY_ROLE holder revoke GUARDIAN_ROLE and passes every other revocation to the role's admin, and unpause accepts it beside the admin. It cannot revoke another role, grant a role, change the hook or upgrade: each reverts with AccessControlUnauthorizedAccount (test_WhenRecoveryRevokesAnyOtherRole_ItReverts, test_WhenRecoveryGrantsAnyRole_ItReverts, test_WhenRecoveryChangesTheHookOrUpgrades_ItReverts).

Single keys. The contract does not look at who holds a role. The post-deploy check asks only the account the deployment names for MINTER_ROLE, BURNER_ROLE or AGENT_ROLE: if that account holds the role and does not answer getThreshold() with at least 2, the check refuses it, unless the profile names the role as an exception. Every profile in ignition/profiles.ts names all three, for its test keys, so with those profiles the check refuses none of them. See Deployment and governance.

During a pause

  • Refused: every movement whose kind is not FORCED. That covers transfers, mints, burns (the burner's too), executed intents, and vault deposits and redemptions. canSend and canReceive answer false.
  • Still possible: forcedTransfer and the 7540 vault's own FORCED recoveries, setFrozenTokens, approve and permit, cancelIntent on an intent token, role changes, replacing the hook and upgrades. The rules still run on a forced movement, so the receiver must still pass them.
  • Lifting it takes a timelock operation: the main timelock, or the recovery timelock if the guardian keeps cancelling. There is no automatic expiry.

Replacing the hook

setPolicyHook(_newHook) needs DEFAULT_ADMIN_ROLE, the timelock. The hook must not be the zero address (PolicyGated_ZeroAddress), its code hash must be attested as HOOK in the token's registry (PolicyGated_NotAttested), and it must name the same registry (PolicyGated_HookRegistryMismatch(_hookRegistry, _tokenRegistry)), because a hook shared by several tokens checks their rules against its own registry.

The hook keeps the rule list of each token itself, and the swap does not copy it. As the token's admin, the timelock sets this token's list on the other hook with setRules. Until it does, that hook refuses every movement of the token with NO_RULES.

When the token is first set up, its initialiser installs the hook with the same checks and then calls setRules(token, rules) on it, so the token is live with its policy as soon as it exists. An empty list skips that call, and the hook's state stands: with no rules, every movement is refused. See ComplianceHook.

Upgrades

Each token is a proxy: a small contract that holds the balances and forwards every call to shared code, its implementation. An upgrade points the proxy at other code (OpenZeppelin UUPS, upgradeToAndCall). The base checks three things, in this order (_authorizeUpgrade):

  1. The caller holds UPGRADER_ROLE, which the deployment gives to the main timelock. The post-deploy check confirms that none of the deployment's wallets also holds it. AccessControl keeps no list of holders, so this is not a check of every account.
  2. The target's code hash is attested as IMPLEMENTATION (PolicyGated_NotAttested(newImplementation, IMPLEMENTATION)). A UUPS implementation records its own address, so each deployment of it has its own code hash and needs its own attestation (test_WhenAnImplementationIsRedeployed_ItNeedsItsOwnAttestation).
  3. The target reports the same templateId() as this token (Templated_WrongTemplate(newImplementation, expected, actual)). The id is keccak256 of the template's name with no version, so a bug-fix release of a template passes, while an intent token cannot be moved onto a vault's code even when that code is attested (test_WhenUpgradedToAVaultImplementationThatIsAttested_ItIsRefused). Code with no templateId() is refused too (test_WhenTheImplementationHasNoTemplateId_ItIsRefused).

OpenZeppelin then checks that the target is a UUPS implementation (UUPSUnsupportedProxiableUUID, ERC1967InvalidImplementation) and emits Upgraded. Value sent with an upgrade reverts (test_WhenTheUpgraderAttachesEther_TheUpgradeReverts).

Standards it speaks, and multicall

  • ERC-7943 (uRWA, the fungible interface): forcedTransfer, setFrozenTokens, getFrozenTokens, canSend, canReceive, canTransfer, with the events ForcedTransfer and Frozen and the error ERC7943InsufficientUnfrozenBalance. The interface also declares the optional errors ERC7943CannotSend, ERC7943CannotReceive and ERC7943CannotTransfer. The token does not use them and rejects with PolicyGated_TransferRejected(reason), which carries the reason.
  • ERC-165: supportsInterface answers true for IPolicyGated, IERC7943Fungible (0x3edbb4c4), IERC20, IERC20Permit, IAccessControl and IERC165. An IntentToken adds ITransferIntent.
  • ERC-2612 permit: approval by signature. Its EIP-712 domain is the token name, version "1", the chain and the token address, the same domain as signed intents.
  • Multicall: multicall(data) runs each call on the token itself, so the caller stays the sender and its roles apply to each call. A minter can mint to several accounts, or an agent can set a frozen amount and force a transfer, in one transaction; the tokens have no batch functions of their own. If one call fails, all are undone (test_WhenALaterCallFails_TheEarlierOnesAreUndone). Each movement inside goes through _move on its own, with its own kind and the balances the previous call left (test_WhenAForcedTransferIsFollowedByAPlainTransferInOneBatch_TheSecondIsPlain). It is not payable, and it cannot initialise the token again (test_WhenABatchCallsInitialize_ItReverts). A contract that filters which functions an account may call on the token has to treat multicall as a way in.

Why it is built this way

  • One path, shared with the pre-flights. The write and the pre-flight answers build the context and run the checks with the same functions (_context, _check), so they do not drift apart. The difference that remains is the ERC-7943 balance case above.
  • No policy in the base. The base checks mechanical things: pause, the frozen bound, roles, attestations. Each question of who, where or when is a rule in the hook, so policy can change without upgrading the token.
  • Balances travel in the context. Rules read both balances from extra and work out the balances after the move from amount, with no call back into the token for them.
  • Kinds travel as arguments. A forced transfer and an intent need a kind the addresses cannot show. _moveAs and _mintAs pass it straight to _move, so no later movement can pick up a stale kind. The one transient value is the reentrancy guard, from OpenZeppelin's ReentrancyGuardTransient.
  • The registry is asked at install time. A hook is checked when it is installed and an implementation when it is upgraded to. A later withdrawal of an attestation does not change a running token: governance removes the component and the guardian can pause meanwhile, so a revocation does not silently drop a check or block every transfer.
  • The registry is fixed at setup. The initialiser takes it once, and there is no setter.
  • Reason codes do not default to yes. A hook or rule that forgets to set its answer returns zero, which is not TRANSFER_OK, so it refuses.
  • Namespaced storage. The registry, the hook pointer and the frozen amounts live in one ERC-7201 namespace (gated.storage.PolicyGatedERC20), apart from the OpenZeppelin parents and the templates.

What it does not do

  • It has no policy of its own to fall back on. A token whose hook holds no rules for it refuses every movement with NO_RULES.
  • It puts no delay or limit on the operational roles. mint, burn, forcedTransfer and setFrozenTokens act at once, for any amount the rules accept. What limits them is who holds the role and the rule list: a supply cap on a mint, or a credential on the receiver of a forced transfer (test_WhenAForcedMoveHasAnIneligibleReceiver_ItIsRejected).
  • A pause blocks the burner too. Enforcement during a pause is forcedTransfer to a quarantine account that passes the rules, and the burn waits for the unpause.
  • canTransfer can say yes where the write reverts, as the table above shows. An integrator that wants to know whether a movement will succeed should call canTransferWithReason.
  • The pre-flights do not model every caller. They simulate from moving its own tokens. They do not check an allowance, and they do not model a spender as operator, forcedTransfer, or a burner burning another account's tokens. A zero to reads as a burn, while transfer to the zero address reverts with ERC20InvalidReceiver.
  • The pre-flights answer for the latest block, and a write lands in the next one. At a time boundary, such as the end of a lockup, they can differ by one second (test/nodejs/time.test.ts).
  • A BURNER_ROLE holder's own burns count as enforcement. The base and the rules ask who the operator is, not why it is burning. Burner accounts are issuer service accounts and should not also be used as investors.
  • A forced transfer to the same account still releases. _releaseFrozen does not look at the receiver, so a forcedTransfer(a, a, amount) the rules accept lowers the frozen amount of a by the usual rule, with its Frozen event, although no tokens leave.
  • A plain holder has no burn. burn needs BURNER_ROLE. A holder's own burn exists on the vaults, as a redemption.
  • The upgrade check trusts what the target reports. It compares the id the target returns, so an attested implementation that reports the same id passes. The review behind the attestation is the control on what that code does, and storage layout is checked off-chain (npm run validate:upgrades), not by the contract.
  • It does not catch a failing hook. A hook or rule that reverts stops the movement and the pre-flights, instead of answering with a reason. Attested ones are expected not to. IERC7943Fungible says canSend and canReceive never revert, which here depends on that expectation.
  • It keeps no history of balances. There are no snapshots. A distribution works from a list built off-chain at the record date (Distributor).
