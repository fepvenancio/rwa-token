Gated4626Adapter

An ERC4626Adapter for a target that is a Gated4626Vault of the same issuer. It is fresh only while that vault deals, so a fund that invests through it stops when the fund it invests in stops.

contracts/portfolio/Gated4626Adapter.sol immutable, not a proxy attested as ADAPTER priced: reported() is false one function overridden: fresh()

In one minute

A fund can be built in two levels. One vault, the master, holds the investments. Other vaults, its feeder classes, each have their own investors and their own fees, and keep nothing themselves: a class's Portfolio has one adapter, into the master. The plain adapter is wrong for that. A master that cannot price its own portfolio holds its last price and stops dealing, but it still answers previewRedeem with that held price, so the plain adapter reads it as fresh and the class goes on taking deposits and paying redemptions at a price the master itself will not deal at. This adapter asks the master whether it deals, and is not fresh when it does not. Everything else is the plain adapter's code.

When it is fresh

fresh() is the plain adapter's answer, that the position can be priced, and also that the target deals. The target is read with five views it already has, and its portfolio with two. Each read is one that cannot revert, and a read that fails counts as "does not deal".

The target's portfolio is asked for on every call and never stored, so a master that replaces its portfolio takes its classes with it, and in the gap between the two calls of a replacement the classes stop (test_ItFollowsTheTargetToANewPortfolio, test_AClassFollowsItsMasterToANewPortfolio).

What not being fresh does is the portfolio's and the vault's business, as for any adapter: the class's priceFresh() is false, so the class holds its last counted value, its max* views read zero and deposits and withdrawals revert, until the master deals again.

A class and its master

  • Two credentials on the master. The master's shares are gated like any other. The adapter holds them, so the master's policy must accept the adapter. A redemption pays the class's portfolio, which is not the shares' owner, and a master refuses a third-party receiver its policy does not accept, so it must accept the portfolio too. A class with the first and not the second can invest and cannot leave, and maxRedeem does not show it (test_AClassWhoseAdapterTheMasterDoesNotAdmitCannotInvest, test_AClassWhosePortfolioTheMasterDoesNotAdmitCannotLeave). The post-deploy check reads both.
  • The price follows the master. A gain reaches every class in proportion and a loss reaches them at once (test_AGainInTheMasterReachesBothPricesInProportion, test_ALossInTheMasterReachesBothAtOnce). Each class has its own rate limit on counted gains. With equal limits a class never runs ahead of its master. One counted less often trails it by the compounding until the gain is all counted, which the accrue keeper keeps small.
  • Fees are each class's own. A class's FeeModel charges on that class's counted value, and one class's fee does not touch another's price (test_OneClasssFeeDoesNotTouchTheOther). The fee is paid from the class's idle money, so the allocator first brings that much back from the master (test_AFeeIsPaidFromMoneyBroughtBackFromTheMaster).
  • Leaving is one call. With the adapter as the class portfolio's liquidity adapter, a holder's redeem on the class pulls from the master in the same transaction (test_AnInvestorLeavesThroughTheMasterInOneCall).

What it does not do

  • It does not close a class when a small write-off closes its master. A master whose portfolio writes off an adapter is exit-only for good, whatever the size. A class sees only the fall in price, and closes its own deposits only when that is more than half. The adapter cannot say "no deposits": not being fresh would stop redemptions too, and holders must be able to leave. So it is a rule for the operator: the timelock batch that writes off an adapter on a master also sets each class's CredentialRule policy to one that trusts no attester. That admits no receiver, so no deposit, and still lets every holder redeem (test_ASmallWriteOffClosesTheMasterAndNotItsClasses pins that the class still takes them).
  • It does not follow a change in the vault's rule. The third row of the table copies the vault's own condition for a read of nothing. The adapter is immutable and the vault can be upgraded, so an upgrade that changes when a Gated4626Vault stops dealing needs a new adapter, attested and swapped into each class.
  • It does not check that its target is a Gated4626Vault. A target without those views fails the reads, and the adapter is never fresh. The council's attestation and the post-deploy check are what tie it to a master.
  • It does not make a class a holder the master counts specially. To the master the adapter is one holder among others.
  • Everything the plain adapter does not do holds here too: it does not judge the target's price, and it does not look at its own vault's pause.
