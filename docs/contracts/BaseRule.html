Contracts / Policy

BaseRule

The parent every compliance rule is built on. It holds the one access check a rule needs, sensible defaults for everything a rule may leave out, and the ERC-165 answer that says "I am a rule".

contracts/hooks/BaseRule.sol abstract: never deployed on its own no admin, no state each rule built on it is attested as RULE

In one minute

A rule is a small contract that answers one compliance question about a movement of tokens. Many tokens share the same rule contracts, and many tokens share one hook, the contract that asks the rules. So a rule must be careful about who may tell it that a movement happened. BaseRule settles that once for every rule: it asks the token named in the movement which hook it uses, and accepts the call only from that hook. Each rule then keeps its records under the token's address, so even a caller who builds a fake token can only ever touch the fake token's records.

How the hook check works

Rules have two kinds of entry point. check, checkSend and checkReceive only read, so anyone may call them. after_ is the one that may write: the hook calls it after the balances moved, for rules that asked for it. BaseRule guards it with the onlyHook(ctx) modifier, which asks ctx.token for its current hook (policyHook(), a read-only call) and compares the answer with the caller.

  1. One read per call. The check is one read-only call to the token, and only rules that want after_ pay it, because the hook never calls after_ on the others.
  2. A wrong caller reverts. Anyone but the token's current hook gets ComplianceRule_OnlyHook(caller).
  3. Sound only with per-token state. Case 3 is harmless because every rule keys what it stores by ctx.token. A rule that kept one shared record for all tokens could be written through a fake token, so the interface requires the per-token key. The one rule whose count is shared by several tokens, FundHoldersRule, keeps it in the Fund, which accepts updates only from its installed rule and only for a registered class; a fake token's call is refused there.

What a rule is told about a movement

The token builds a TransferContext for every movement and the hook hands it to each rule unchanged. On a movement, a rule receives it only through the hook. Anyone can call check with a context of their own, which only reads, and a call to after_ passes only from the hook that ctx.token names. The fields are token, from, to, id (0 for these fungible tokens), amount, operator (the account driving the movement), kind and extra. extra starts with both balances before the move, so a rule works out the balances after it from amount and never has to call back into the token for them. The kind says what sort of movement it is:

What a rule must promise

The interface sets the contract between the hook and a rule. BaseRule cannot enforce all of it, so the council reviews each rule against it before attesting it.

  • check is read-only and never reverts on a decision. It returns TRANSFER_OK or a reason code. It must not revert even for an amount above the sender's balance: the write never offers the hook such an amount, but the token's canTransfer does, so a rule compares before it subtracts.
  • The account questions agree with check. If checkSend or checkReceive refuses an account, check refuses every movement on that side of a kind the rule does not exempt. They take no amount and must not encode a quantitative rule (a count, a balance, a limit), which ERC-7943 keeps out of the account questions.
  • State is keyed by ctx.token. The shipped rules other than FundHoldersRule authorise their per-token settings by the token's own roles, asked live with hasRole; FundHoldersRule keeps its settings in the Fund, under the Fund's owner.
  • after_ never calls back into the token to move anything. It runs inside the token's reentrancy guard, so a transfer from it would revert.
  • ruleId() names the rule type. A hook takes one rule of each type per token.

Why it is built this way

  • Rules do not store their hook. Because onlyHook asks the token, a rule has no hook address built in. One deployed instance serves every token, keeps working when a token moves to a new hook, and its code hash, which the council attests, does not depend on any hook.
  • Rules are plain contracts, not proxies. They are attested by code hash, so the reviewed code is the code that runs. Changing a rule means deploying a new one, having it attested, and swapping it in with the hook's setRules.
  • Defaults that do nothing harmful. A rule that has no account-level opinion accepts there, and check still decides every movement. A rule that does not want after_ costs nothing after the move.
  • A forgotten answer refuses. Every reason code is the hash of its name, so TRANSFER_OK is not zero. A rule that forgets to set its return value returns zero, which the hook reads as a refusal.
