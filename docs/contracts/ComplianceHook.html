Contracts / Policy

ComplianceHook

The policy desk every token asks before a balance moves. One hook serves all the tokens of a deployment. It keeps an ordered list of reviewed rules for each token, asks them in turn, and passes on the first refusal.

contracts/hooks/ComplianceHook.sol immutable, not a proxy no admin of its own: each token's admin sets that token's rules attested as HOOK

In one minute

A token here does not decide on its own who may hold it. Before every transfer, mint or burn it asks a separate contract, the hook. The hook holds, for each token, a short ordered list of rules: small contracts that each check one thing, such as "does the receiver hold an accepted credential" or "is this holder locked up". The hook asks the rules one by one. If all say yes, the movement goes ahead. The first rule that says no stops it, and its reason code is what the caller sees. Only rules the security council has reviewed and registered (attested) can be put on a list, at most 16 per token, and only the token's own administrator can change its list, which after deployment means a delayed governance operation.

How one movement passes through the list

The diagram follows one transfer of the intent token, whose deployed list has five rules. Every movement kind takes the same path: transfers, executed intents, forced transfers, mints and burns. The pre-flight answers (canTransferWithReason, canExecute) ask the same beforeTransfer, so they give the same answer the write would.

  1. The token checks first. The token's own mechanical checks (pause, the unfrozen balance) run before the hook. The token reads its hook address once per movement, so the hook that approves a movement is the hook that sees its afterTransfer.
  2. The list of this token. beforeTransfer(ctx) looks up the list kept for ctx.token. A token with no rules gets NO_RULES, so every movement is refused until a list is installed.
  3. Rules in order, read-only. The hook calls check(ctx) on each rule in list order and returns the first reason that is not TRANSFER_OK. beforeTransfer and check are view functions, so the EVM runs them as static calls and a rule cannot change any state while it decides.
  4. Balances move, then bookkeeping. After the move the token asks wantsAfter(), which the hook answers for the calling token from its after mask. If any bit is set, the token calls afterTransfer(ctx). The hook refuses that call from anyone but the token named in the context (ComplianceHook_OnlyToken), and calls after_ in list order on the rules whose bit is set. This runs inside the token's reentrancy guard, so a rule cannot call back into a transfer.

The lists the deployment installs

The deployment scripts pass each token its list in the token's setup data (RULE_ORDER in ignition/modules/roles.ts). The token installs the list on the hook while it is being set up, and ProxyDeployer refuses to finish unless the hook ends up holding exactly that list for the new token.

Changing a token's list

A list is never edited in place. setRules(token, rules) replaces the whole list, and every check below runs before the call can succeed. One bad entry fails the whole call, so a token never ends up with half a list.

  1. Who is asking. The caller is the token itself, or holds DEFAULT_ADMIN_ROLE on the token. The hook asks the token at call time (hasRole, a read-only call), so it keeps no admin list of its own and follows the token's role changes. An address with no code cannot be asked, so only that address itself could set its list. Otherwise: ComplianceHook_NotTokenAdmin(token, caller).
  2. How many. At most 16 rules (ComplianceHook_TooManyRules(count)).
  3. Reviewed rules only. Each rule's code hash must be attested as RULE in the registry (ComplianceHook_NotAttested(rule)).
  4. One of each kind. No two rules may share a ruleId(), which names the rule type (ComplianceHook_DuplicateRule(rule)). The same contract listed twice fails the same way.
  5. Store and announce. The old list is cleared, the new one stored in order, and each rule's wantsAfter() is read once and recorded as a bit of the after mask. Emits RuleSetChanged(token, ruleIds) with the new rule ids in order.

The token itself calls setRules only from its setup function, which installs the hook and then the initial list in the same call; that is why the hook accepts the token without asking for a role: the token is the caller, and it holds no role on itself. After the deployment hands each token to the main timelock, the timelock is the only holder of DEFAULT_ADMIN_ROLE, so every later change is a governance operation with its delay. The governance multisig calling the hook directly is refused. Passing an empty list is allowed and makes the token refuse every movement with NO_RULES.

Replacing the hook itself is the token's setPolicyHook, also under DEFAULT_ADMIN_ROLE. The token accepts only a hook attested as HOOK whose REGISTRY() is the token's own registry. A second hook built on the same registry has the same code hash, so the council's one attestation covers it. The token's list must be set on the new hook before the swap; otherwise the token refuses every movement with NO_RULES from the moment the swap takes effect.

The account questions

ERC-7943, the standard the tokens implement, asks two questions that take no amount: may this account send at all, and may it receive at all. The token answers them with canSend and canReceive, which are false while the token is paused or has no hook, and otherwise ask the hook's checkSend(token, account) or checkReceive(token, account). The hook walks the same list in the same order and calls each rule's own checkSend or checkReceive. A rule with no opinion about an account on its own, like the minimum position or the window, accepts every account there.

Why it is built this way

  • One hook, one review. The registry is the hook's only fixed setting, so every hook built on the same registry has the same code hash. The council attests it once for the whole deployment, and a new token needs one setRules, not a new hook.
  • Everything is kept per token. The lists and the after masks are stored by token address. A token can set its own list and no other, and one token's afterTransfer cannot run another token's rules (tests cover both).
  • It fails closed. An empty list refuses everything. A rule that is not attested, or a duplicate, fails the whole setRules call.
  • The after mask is fixed at install. Reading wantsAfter() once, when the list is installed, saves a call per rule on every movement, and a rule cannot start or stop asking for after_ later. The count and the mask share one storage word.
  • Attestation is checked when a rule is installed, not on every transfer. Withdrawing an attestation does not silently drop a rule from a running token; governance removes it with setRules, and the guardian can pause the token meanwhile.
  • A hard cap of 16. Every loop in the hook runs over at most 16 rules, so the cost of a movement has a known upper bound.
