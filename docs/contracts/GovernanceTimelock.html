Contracts / Governance

GovernanceTimelock

The main timelock. Every governance change waits here for a fixed delay before it runs, and the guardian can cancel it during the wait. It is OpenZeppelin's TimelockController with two additions: its delay can never be below seven days, and a second, recovery timelock may take away a canceller's right to cancel.

contracts/governance/GovernanceTimelock.sol immutable, not a proxy admin: itself after deployment not attested: nothing installs it by code hash

In one minute

A timelock is a contract that holds admin powers and uses them only after a public waiting period. The governance multisig proposes a change, the timelock records it, and once the delay has passed (7 days by default) governance executes it. While it waits, anyone can see what is coming, and the guardian, a multisig that can only stop things, can cancel it. That cancel power has one weak spot: the guardian could cancel its own replacement. So a second timelock exists, with the same delay and nobody able to cancel it, which can do only a few undoing things: unpause, take the guardian's role away, clear a guardian block or revive an attester in the credential registry, and take its cancel right on this timelock.

How it works

Two timelocks, one proposer. Governance proposes and executes on both. On the main timelock the guardian can cancel; on the recovery timelock nobody can, but it reaches only a handful of functions.

  1. Propose. A PROPOSER_ROLE holder calls schedule or scheduleBatch with the target, the call data and a delay. A delay shorter than the timelock's minimum is refused (TimelockInsufficientDelay).
  2. Wait. The operation is public from the moment it is scheduled. Executing it early fails with TimelockUnexpectedOperationState.
  3. Cancel, perhaps. A CANCELLER_ROLE holder can cancel any operation that is scheduled and not yet executed, including one whose delay has already passed.
  4. Execute. An EXECUTOR_ROLE holder calls execute or executeBatch, and the timelock makes the calls itself. A batch runs all its calls or none.

Roles as deployed

The Components deployment module creates the recovery timelock first, then the main timelock, which names it. Activate finishes the setup and the deployer account gives up its admin rights on both.

The guardian can cancel on the main timelock but cannot propose or execute there, and holds no role at all on the recovery timelock. The post-deployment check (assertHandedOver in test/nodejs/fixtures.ts) asserts the guardian's roles, the recovery timelock's roles and the absence of cancellers on it, the deployer's renunciation and both delays; it does not check governance's roles on the main timelock.

The delay

The delay is a deployment parameter, minDelay in the Components module, 7 days (604,800 seconds) unless the deployment sets another value. Both timelocks start with the same value, so at deployment the recovery path is no faster than the normal one. Only the main timelock has a floor.

  • What enforces it per operation: OpenZeppelin refuses to schedule anything with a shorter delay than the current minimum, and refuses to execute before the scheduled time.
  • What checks the 7 days: the main timelock refuses less than seven days, at deployment and in updateDelay (GovernanceTimelock_DelayBelowFloor(delay, floor)). The recovery timelock is OpenZeppelin's own and has no floor; its powers only undo the guardian's. The post-deployment check asserts getMinDelay() ≥ 7 days on both timelocks.
  • Changing it later: updateDelay accepts only a call from the timelock itself, so a new delay is an ordinary operation: it waits out the current delay, and on the main timelock the guardian can cancel it. On the main timelock a new delay below seven days reverts when the operation runs.

The guardian as canceller

The guardian is a multisig whose powers all stop things and take effect at once: it pauses tokens and both executors, it can block a subject or switch off an attester in the credential registry, and on this timelock it can cancel. It cannot unpause, grant roles, change hooks or upgrade. Those are timelock operations.

Cancelling is what makes the delay a safeguard: a harmful operation can be stopped before it runs. But it also lets the guardian cancel the operation that would replace it, or that would unpause a token it paused. That is the case the recovery timelock exists for.

The recovery timelock

A plain OpenZeppelin TimelockController, with the same delay and governance as proposer and executor, and no cancellers. It holds RECOVERY_ROLE in seven places: each of the three tokens, both executors, the credential registry, and this timelock. Apart from being its own admin, it holds nothing else anywhere, and nothing on PolicyRegistry.

WhereRECOVERY_ROLE allows exactly
Each token, IntentExecutor, DvPExecutorunpause(), and revokeRole(GUARDIAN_ROLE, account)
CredentialRegistryrevokeRole(GUARDIAN_ROLE, account), clearGuardianBlock(subject), reviveAttester(id)
Main timelock (GovernanceTimelock)revokeRole(CANCELLER_ROLE, account)

It cannot grant any role, change a hook, upgrade, or propose, execute or cancel on the main timelock; the tests try each and expect AccessControlUnauthorizedAccount. Each unpause in a recovery batch must target something that is paused when the batch runs, otherwise OpenZeppelin's ExpectedPause reverts the whole batch. Until the batch executes, the guardian keeps all its powers.

Recovery bounds the guardian, not governance. The governance multisig proposes and executes on both timelocks, so a compromised governance multisig is outside what this control protects against.

Why it is built this way

  • OpenZeppelin, plus a constructor check and two overrides. The constructor refuses a delay below seven days and grants RECOVERY_ROLE. revokeRole lets RECOVERY_ROLE revoke CANCELLER_ROLE and nothing else, then falls through to OpenZeppelin for every other case. updateDelay runs OpenZeppelin's version, caller check first, then refuses a delay below seven days. So every power held here waits at least seven days.
  • RECOVERY_ROLE is not a role admin. A role admin could also grant the role it administers. Revoking is the smallest power that gets governance past a guardian that cancels its own replacement. Its own admin is DEFAULT_ADMIN_ROLE, the timelock itself, like every other role.
  • No cancellers on the recovery timelock. If anyone could cancel there, the guardian problem would only move. It starts with the same delay, so at deployment it is no shortcut around the main timelock; it has no floor of its own.
  • The guardian is stop-only. Every power it has takes effect at once and only stops something. Everything that starts or changes something waits for a timelock.
