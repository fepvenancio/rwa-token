Contracts / Policy

FundHoldersRule

The fund-wide investor cap. It lets a new investor into any class of a fund only while the fund has room, and tells the fund each time someone starts or stops holding a class.

contracts/hooks/rules/FundHoldersRule.sol immutable, not a proxy cap and exemptions set on the Fund by its owner attested as RULE ruleId: keccak256('FundHoldersRule.v1')

In one minute

A fund may be allowed only so many investors, counted across all its share classes. In the deployment this rule is the last one listed on every class of the fund. Before a movement it asks the Fund one question: would the receiver be a new investor, and if so, is there room? After the movement it tells the fund that someone now holds a class, or has stopped holding one.

The count and the cap live in the fund, not in the rule, so the rule can be replaced without losing the count. An investor already in the fund is never refused for the cap, whichever class it moves into, and the issuer's forced transfers are never capped.

How a movement is decided

check(ctx) reads the fund once, with admission(token, to), which returns the token's class number, the receiver's class mask and exempt flag, the count, the cap and the fund's installed rule. Only at a full fund does it read the fund a second time, for the sender. The balances before the move come from the context the token built (extra), not from the token.

  1. Wrong fund or wrong rule: refuse everything. A token that is not a registered class of the fund, or a rule that the fund has replaced, answers NOT_FUND_CLASS for every movement, zero amounts, burns and forced transfers included. So a retired rule never says yes in a pre-flight while its write would be refused, and a class cannot hold any balance before the fund records it.
  2. Who is a new investor. A receiver that holds no class of the fund and is not exempt, receiving a non-zero amount from someone else. The class token itself is never one: Gated7540Vault keeps the shares of pending redemptions at its own address.
  3. Room, or a free slot. Below the cap a new investor passes. At the cap it passes only if the sender leaves the fund in the same move: the sender is not the zero address, not the class itself, not exempt, holds no other class, and moves its whole balance. A sender who keeps another class stays an investor and frees nothing.
  4. Above a lowered cap, nobody new. When the owner lowers the cap below the count, no new investor is admitted, even by a move that would be net zero, until the count is back down. Existing investors can still trade among themselves and leave.

What each kind of movement meets

Every kind first meets the class check of step 1.

KindThe capRecorded after the move
TRANSFERapplies to a new investor, net of a sender who leaves the fundthe receiver joins the class if it held none of it; the sender leaves it if it moved all of it
EXECUTEDthe same as a transferthe same as a transfer
MINTapplies to a new investor; a mint has no sender to free a slotthe receiver joins
BURNnever: a burn has no receiverthe sender leaves if it burnt all of it
FORCEDnever: enforcement is exemptboth sides, so the count can end above the cap

A vault deposit is a MINT of shares, a 4626 redemption a BURN, and a 7540 redemption request a TRANSFER into the vault, which step 2 lets through because the receiver is the class itself. When the agent delivers a stranded 7540 deposit with recoverClaimable, that is an enforcement mint, so it is exempt from the cap and still counted. An integration test runs exactly that: a deposit fulfilled while the fund had room, then the fund filled through the other two classes, the claim refused with MAX_HOLDERS, and the agent's recovery taking the count above the cap.

After the move: telling the fund

The rule's wantsAfter() is true, so the hook calls its after_ once the balances have moved, inside the token's guard against reentry.

  1. Nothing to record. After the hook check, a zero amount or a move to oneself returns without touching the fund.
  2. The zero-address guards. join is called only when to is not the zero address, so a burn joins nobody, and only when the receiver's balance before the move was zero. leave is called only when from is not the zero address, so a mint leaves nobody, and only when the amount equals the sender's whole balance before the move. Both balances come from extra.
  3. The fund's own checks. join and leave revert unless the caller is the fund's installed rule (Fund_OnlyRule) and the token is a registered class (Fund_NotAClass); a revert there undoes the whole movement. A class joining itself, such as shares going into the 7540 escrow, is ignored, and a leave for it changes nothing.

The rule has no setter and no admin of its own. The cap, the exemptions, the classes and which rule is installed are all set on the Fund by its owner, which after deployment is the main timelock, so every change waits for its delay.

Reason codes

CodeWhen
NOT_FUND_CLASSThe token is not a registered class of this rule's fund, or the fund's installed rule is another one. Every movement, every kind, any amount.
MAX_HOLDERSA new investor while the cap is 0, or while the count is at the cap and the move is not net zero, or while the count is above the cap.

The account questions answer only the class check

The token's canSend(account) and canReceive(account) come from ERC-7943, which keeps quantitative rules, such as balance checks and amount limits, out of those two questions. A cap on investors depends on the movement, not only on the account, so it belongs to check alone. checkSend and checkReceive therefore answer only whether the token is a class of the fund under this rule.

At a full fund, canReceive is still true for a new investor, while a mint or a partial transfer to it is refused with MAX_HOLDERS. The pre-flight canTransferWithReason says MAX_HOLDERS too. The vaults' maxDeposit tests a mint, which does reach check, so it reads 0 for that investor, and Gated7540Vault refuses its deposit request up front.

Replacing the rule

The rule holds no state, only the fund's address, so a replacement starts with the count and the masks as they are. The fund names one installed rule at a time, and this rule compares itself with it on every movement. While a class's rule list still names a rule the fund has replaced, that rule answers NOT_FUND_CLASS to everything, forced transfers included, and the class is closed. The change is therefore one main-timelock batch: fund.setRule(newRule) together with hook.setRules for every class. A second instance for the same fund has the same code hash, so it is already attested. Fund has the details, and Fund.firstBrokenClass() names any class whose list does not name the installed rule.

Why it is built this way

  • The investor count that matters is fund-wide. One investor in three classes is one investor. Only a record shared by all the classes can see that, so the count lives in Fund and each class lists this one rule.
  • State in the fund, policy in the rule. The rule can be replaced without losing the count, and the fund cannot be written by anything but the installed rule.
  • Fail closed on a mismatch. A token that is not a class, or a rule other than the fund's installed one, refuses every movement rather than letting balances move uncounted. The pre-flight calls give the same answer as the write.
  • Never in the way of an exit or of enforcement. Only a new investor meets the cap. Existing investors trade and leave freely, and the agent's forced transfers are exempt, though counted.
  • Few reads. One admission call answers the usual case, and the fund keeps the rule, the count and the cap in one storage word. The sender is read only at a full fund. Balances come from the context, so the rule never asks the token for one.
  • Last in the list. In every deployed list it comes after the credential rule, the minimum position, the holder restrictions and, on the intent token, the settlement window, so a receiver who cannot hold the token at all is refused for that reason before the cap is consulted.
  • One instance per fund. The fund's address is an immutable, so it is part of the attested code hash. The council reads the fund's code and owner before it attests the rule.

What it does not cover

  • Investors are addresses. One investor with two wallets counts twice, and an omnibus wallet counts once.
  • Dust can take a slot. Any non-zero balance makes an investor. On a class whose minimum position is 0, a tiny transfer to an eligible address takes a slot for as long as it is held; the agent can take it back with forcedTransfer. The deployed lists put MinPositionRule before this rule for that reason, and it does nothing until a minimum is set.
  • A class whose list drops this rule is uncapped. The hook accepts any list of attested rules. A class whose list does not name the fund's rule moves uncounted, and the fund's count goes stale. Fund.isClassIntact and firstBrokenClass report it; nothing prevents it.
