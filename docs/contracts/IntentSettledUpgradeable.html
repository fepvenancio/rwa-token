Contracts / Token

IntentSettledUpgradeable

Lets a holder authorise a transfer by signing a message instead of sending a transaction. An approved executor submits the signed message, and the token checks it, field by field, before the transfer goes through the same compliance checks as any other.

contracts/mixins/IntentSettledUpgradeable.sol abstract mixin, used by IntentToken role: EXECUTOR_ROLE, administered by the main timelock attested as part of the IntentToken implementation

In one minute

An intent is a transfer instruction the holder signs with their key: "send this amount to that account, before this deadline". Signing costs nothing and needs no transaction. The issuer's settlement system then submits it through an executor, a contract the token has authorised, at the time it chooses.

The token checks that the intent has not expired, has not been used or cancelled, is submitted by the executor it names, and carries the holder's valid signature. Then the transfer runs through the compliance hook like any other movement, labelled EXECUTED. The executor cannot change a single field: any change breaks the signature. Until it runs, the holder can cancel it.

How an intent is settled

Four parties take part. The holder signs. An operator key (an issuer or relayer key with OPERATOR_ROLE on the executor) submits. The executor contract holds the token's EXECUTOR_ROLE and calls the token. The token runs the checks and asks the hook.

  1. Sign. The holder's wallet signs the intent as EIP-712 typed data, structured data the wallet can show field by field. intentHash(intent) returns the digest the token expects.
  2. Optional pre-flight. canExecute(intent, sig) runs the same checks without writing. It treats its caller as the executor, so the operator asks it as a read-only call from the executor's address.
  3. Submit. The operator calls execute(token, intent, sig) on the IntentExecutor. It checks its own OPERATOR_ROLE and pause, refuses an intent that states a consideration (IntentExecutor_ConsiderationNotSupported), and calls executeTransfer.
  4. Check and move. The token runs the checks below, marks the nonce used, and moves the tokens as EXECUTED through the base's single movement path, where the pause, the unfrozen balance and the hook decide.
  5. Record. The token emits IntentExecuted(intentHash, from, to, amount, executor, ref), where executor is the account that called the token, and returns the intent hash.

The checks, in order

executeTransfer and canExecute run the same checks in the same order. The first one that fails decides the answer. The tests pin the order pair by pair, and a fuzz test checks that canExecute returns exactly the reason executeTransfer reverts with, or success when it succeeds.

  • Times are inclusive. The intent can run at the exact second of deadline and at the exact second of validAfter. An intent whose validAfter is later than its deadline can never run.
  • Step 8 is the ordinary movement path. An amount within the balance but above the unfrozen part reverts with ERC7943InsufficientUnfrozenBalance, an amount above the balance with ERC20InsufficientBalance; canExecute answers INSUFFICIENT_UNFROZEN for both. A zero to reverts with OpenZeppelin's ERC20InvalidReceiver before the pause, frozen and hook checks, which canExecute does not reproduce: it returns whatever those checks say.
  • Any revert keeps the nonce. Marking the nonce in step 7 is undone with everything else when a later step fails. An intent refused because the settlement window is closed can be submitted again once it opens, until its deadline.
  • What canExecute cannot see: whether its caller holds EXECUTOR_ROLE, and the executor contract's own checks (its role, its pause, its refusal of a stated consideration).

What the holder signs

A TransferIntent has ten fields, all fixed-size, signed as EIP-712 typed data with this type string (TRANSFER_INTENT_TYPEHASH is its keccak256):

TransferIntent(address from,address to,uint256 amount,bytes32 nonce,uint256 deadline,bytes32 ref,address executor,uint256 validAfter,address considerationToken,uint256 considerationAmount)
FieldMeaning
fromThe holder: the signer and the sender of the tokens.
toThe receiver.
amountThe number of tokens to move.
nonce32 random bytes the signer chooses. Each value works once for that signer.
deadlineThe last second at which the intent can run.
refA 32-byte reference to an off-chain message, such as the hash of an ISO 20022 message id. It appears in the IntentExecuted event and in the context the rules receive. None of the deployed rules reads it.
executorThe only account allowed to submit it. Zero means any holder of EXECUTOR_ROLE.
validAfterThe first second at which the intent can run. Zero means no lower bound.
considerationToken, considerationAmountWhat the signer is to receive in return for this leg. They are signed, so nobody can change them, but the token never checks the payment itself: only the executor the intent names can enforce it.

The domain ties a signature to one token on one chain: name is the token's name, version is "1", then the chain id and the token's address (the proxy). It is the same domain as ERC-2612 permit on the same token, and the token reports it through eip712Domain() (ERC-5267). A signature made for another chain or another token fails with BAD_SIGNATURE.

Nonces and cancelling

A nonce here is a random 32-byte value that makes each intent unique, in the style of ERC-3009. The token keeps one used-or-not flag per signer and nonce, nothing else. Because nonces are random rather than counted, the signer needs nothing from the chain to sign, can sign many intents at once, and the executor can run them in any order.

  • Executing an intent marks its nonce used, so the same intent can never run twice (NONCE_USED).
  • cancelIntent(nonce) marks one of the caller's own nonces used, so no intent signed with it can run. It needs no other field, works while the token is paused, and emits IntentCancelled(signer, nonce). Cancelling a nonce that is already used reverts with PolicyGated_TransferRejected(NONCE_USED). One account cancelling a value has no effect on another signer's nonce of the same value.
  • A cancel and an execution race: whichever transaction is mined first wins. There is no way to cancel after execution.
  • nonceUsed(signer, nonce) tells whether a nonce is spent. These nonces are separate from the counter nonces(owner) that permit uses.

Naming an executor, and stating a payment

Several contracts may hold EXECUTOR_ROLE on one token. In the deployment that is the IntentExecutor, which forwards intents one by one or in batches, and the DvPExecutor, which settles a security leg against a cash leg in one transaction. Two fields let the holder control which one runs the intent:

executorConsideration (token or amount)Result
zerononeAny EXECUTOR_ROLE holder may run it.
zerostatedNever runs: CONSIDERATION_NEEDS_EXECUTOR.
an addressnone or statedRuns only when that address calls the token; any other caller gets WRONG_EXECUTOR.

The token reads the consideration fields only for that check. It moves one token and cannot see a second leg, so it cannot tell whether the payment happened. An intent that states a payment therefore has to name the executor that will enforce it; otherwise any executor could run it and deliver the tokens without the payment. The IntentExecutor moves one token too, so it refuses every intent that states a consideration, whoever the intent names. The DvPExecutor is the one that checks the two legs describe one trade and runs them together, so the delivery and the payment happen in the same transaction or not at all.

Signature checks

The token uses OpenZeppelin's SignatureChecker, which chooses the method by whether from has code:

  • No code (an ordinary key): the 65-byte signature is recovered with ECDSA. Only the low-s form is accepted, so a valid signature cannot be rewritten into a second valid one.
  • Code (a contract wallet): the token asks the wallet with ERC-1271 isValidSignature(hash, signature). That also covers an ordinary key with an EIP-7702 delegation, which has code; its wallet code must answer ERC-1271, or its intents fail with BAD_SIGNATURE.

Any change to any field, by the executor or anyone else, changes the digest and fails the check.

What the rules see

The mixin moves the tokens with the base's _moveAs(from, to, amount, EXECUTED, ref, deadline), which announces the kind for the single movement path. The hook receives:

FieldValue for an executed intent
kindEXECUTED
from, to, amountFrom the intent.
operatorThe account that called executeTransfer: the executor contract, not the holder.
extraabi.encode(fromBalance, toBalance, ref, deadline): the two balances before the move, then the intent's reference and deadline. Rules that read only the balances decode the first two words.

The consideration fields never reach the hook. Among the deployed rules, the settlement window rule judges only this kind: an executed intent passes only inside the token's daily window, on its enabled weekdays.

Why it is built this way

  • The holder keeps the keys; the issuer keeps the timing. The holder authorises once, off-chain, and pays no gas. Settlement happens when the executor runs the intent, not when it is signed.
  • The executor can only run it or not. Every field is inside the signed digest, so there is nothing an executor can adjust.
  • Message checks live in the mixin, policy lives in the hook. Deadline, nonce, executor, payment field, start time and signature are facts about the signed message, not decisions about who may hold the token, so they are not rules. Once the message is sound, the movement takes the same path as every other and the same rules decide.
  • Binding stops a leg from running alone. An intent written for a delivery-versus-payment trade names the DvP executor, so no other executor can deliver its tokens without the cash leg.
  • Pre-flight never lies. canExecute reuses the private check function and the base's checks, so its answer is the reason executeTransfer would revert with.
  • No state beyond nonces. The mixin stores only the used-nonce flags, in its own ERC-7201 namespace (gated.storage.IntentSettled). Executors hold no intents and no nonces, so replacing an executor loses nothing.
