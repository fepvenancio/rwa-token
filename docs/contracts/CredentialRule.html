Contracts / Policy

CredentialRule

Decides who may hold a token. It reads each party's standing in the credential registry, lets any holder who may leave send, and admits as a receiver only an active address whose record fits the token's own policy.

contracts/hooks/rules/CredentialRule.sol immutable, not a proxy policy set per token by the token's DEFAULT_ADMIN_ROLE attested as RULE ruleId: keccak256('CredentialRule.v1')

In one minute

Every token checks a list of rules before any balance moves, and this rule comes first in every deployed list. It asks two questions. May the sender leave? Yes, unless the registry says nobody ever vouched for the sender or the sender is blocked. May the receiver come in? Only if an attester the token trusts has vouched for it, the record is current, and its qualification flags fit what the token asks for, for example "identity checked, and a professional investor".

Each token has its own policy, set by its own administrator, so one rule serves an open token and a professionals-only fund class side by side. The rule keeps no list of holders. The CredentialRegistry is the record.

How a movement is decided

The token's compliance hook calls check(ctx) with the movement's context: the token, the sender, the receiver, the amount, the account that called the token (the operator) and its kind. The rule checks the sender leg, then the receiver leg, and returns TRANSFER_OK or a reason code. It reads the registry once per party it checks.

  1. The sender may leave. Any standing except NONE and BLOCKED lets an address send: ACTIVE, EXIT_ONLY and LAPSED. The sender's bits, country and attester do not matter, and neither does the token's policy.
  2. The enforcement burn passes. A BURN whose operator holds the token's BURNER_ROLE passes the sender leg whatever the sender's standing. The token is asked about the role only when the sender could not otherwise leave.
  3. The receiver must be active and accepted. The token's policy is read first, so a token with no policy answers RECEIVER_NOT_ELIGIBLE for everyone. Then the standing: LAPSED and every other standing except ACTIVE are refused with different codes. Then the policy itself.

Which leg each kind of movement checks

Zero amounts are checked like any other, and a move from an account to itself checks both legs.

KindSender legReceiver leg
TRANSFERmust be able to leavemust be ACTIVE and accepted by the policy
EXECUTEDthe signer of the intent must be able to leavethe same as a transfer
FORCEDnot checked: the agent can take tokens from a blocked holderchecked: the agent can move tokens only to an accepted receiver
MINTnone: a mint has no senderchecked
BURNmust be able to leave, unless the operator holds the token's BURNER_ROLEnone: a burn has no receiver

The rule never looks at the caller, the spender or the executor, apart from the BURNER_ROLE question on a burn. A vault deposit is a MINT of shares. A 4626 redemption is a BURN; a 7540 redemption request is a TRANSFER of the shares into the vault, which burns them from its own address at fulfilment. So on the vaults a holder whose record lapsed can redeem but cannot deposit, and a blocked holder can do neither.

The token's policy

Each token has one policy in the rule, stored under the token's address. It says which records the token accepts from a receiver.

Who sets it

setPolicy asks the token, at the moment of the call, whether the caller holds the token's DEFAULT_ADMIN_ROLE. While Activate configures the deployment that is the deployer; after the hand-over it is the main timelock, so a policy change is a governance operation with its delay. Because the policy is stored under the token's address, a fake token can authorise anyone to set a policy, but only its own: no other token's policy changes (a test pins this). The call to the token is read-only, so a token cannot change state while it answers.

Removing a policy (attesters set to 0) closes the token to every receiver, existing holders included. A transfer, a signed intent and a 7540 redemption request (a transfer into the vault) are refused with RECEIVER_NOT_ELIGIBLE. Holders can still leave through a burn, which has no receiver: a 4626 redemption, or the burner's burn.

Reason codes

CodeLegWhen
SENDER_NOT_VERIFIEDsenderThe sender reads NONE or BLOCKED, and the movement is not a burn by a BURNER_ROLE holder.
RECEIVER_NOT_ELIGIBLEreceiverThe token has no policy; or the receiver is ACTIVE but its attester is not in the bitmap or its bits do not fit.
CREDENTIAL_EXPIREDreceiverThe receiver's record lapsed: it can still send, burn and redeem, but not receive.
RECEIVER_NOT_VERIFIEDreceiverThe receiver reads NONE, EXIT_ONLY or BLOCKED.

When both legs would fail, the sender's code is the one returned. The codes are defined in Errors.sol; a write that is refused reverts with PolicyGated_TransferRejected(reason), and the token's pre-flight calls (canTransferWithReason, and canExecute for a signed intent) return the same code without moving anything.

Enforcement still works on a blocked holder

A blocked holder, or an address with no record at all, cannot send. The issuer's two enforcement tools still reach it:

  • A burn by the burner. A BURN whose operator holds the token's BURNER_ROLE passes the sender leg. A burn by anyone else, the holder's own vault redemption included, does not.
  • A forced transfer by the agent. FORCED skips the sender leg, so the agent's forcedTransfer can take the tokens. The receiver is still checked, so the tokens can only go to an address the token accepts.

Being able to burn or force does not mean every other rule agrees: a later rule in the token's list, a freeze for example, can still refuse the movement.

The account questions: checkSend and checkReceive

ERC-7943, the standard the tokens implement, has two account-level questions with no amount: canSend(account) and canReceive(account). The token answers them by asking the hook, which asks every rule's checkSend and checkReceive and stops at the first refusal. Both answers are false while the token is paused.

  • checkSend(token, account) is the sender leg: TRANSFER_OK for ACTIVE, EXIT_ONLY and LAPSED, SENDER_NOT_VERIFIED otherwise, for any token.
  • checkReceive(token, account) is the receiver leg under that token's policy.

check is built from the same two pieces, and a fuzz test pins the relation: for a transfer or an executed intent, check is the send answer, then the receive answer; for a burn it is the send answer, or TRANSFER_OK for the burner; for a mint or a forced transfer it is the receive answer. So canSend reads false for a blocked holder although the agent's forcedTransfer can still move its tokens.

What the deployment sets

  • Position in the list. First in all three demo tokens' rule lists (RULE_ORDER), ahead of the minimum position, the holder restrictions, the settlement window on the intent token, and the fund's investor cap.
  • The attester. Activate adds one attester to the registry, the demo KYC provider, as id 0, allowed to assert the eight named bits unless the deployment narrows that.
  • The policies. Activate calls setPolicy(token, KYC, 0, 0, 1) for the intent token and both vaults while the deployer is still their admin: KYC from attester 0, nothing more.
  • Outside the module. The KYC attester writes a record for every holder, and for the Gated7540Vault itself. That vault holds the shares of pending redemptions at its own address, and this rule does not exempt it, so it needs a record the policy accepts.
  • Checked after deployment. The post-deployment check asserts that the rule reads the deployment's registry, that it is attested, and that each token's policy is exactly (KYC, 0, 0, 1).

Until a token has its policy, the rule admits no receiver, so no balance can exist before the token is configured.

Why it is built this way

  • Getting out is the default. The sender leg asks only whether the address may leave. A holder whose record lapsed, or whose attester was killed, can still sell, redeem and settle a signed intent. Only an explicit block stops it, and even then the issuer can burn or force.
  • No running state. The rule stores each token's policy and nothing else: no counts, and its after_ is the empty default from BaseRule, which the hook never calls because wantsAfter() is false. The registry is the state, so a rule taken out of a list and put back misses nothing.
  • One instance for every token. The policy is stored per token and authorised by that token's own admin, so one attested contract serves every token in the deployment.
  • The registry is pinned by the attestation. REGISTRY is an immutable, so it is part of the code the council attested. That pins which registry the rule reads, not that registry's code, which the council reads before it attests the rule.
  • Cheap on the common path. One registry read per party, and the token's BURNER_ROLE is asked only when a burn would otherwise be refused. The registry works out the standing, so the rule does no time or trust arithmetic.
  • Country is not used. The registry stores a country code, and this rule reads only the standing, the bits and the attester id.
