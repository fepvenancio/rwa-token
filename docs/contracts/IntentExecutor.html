Contracts / Settlement

IntentExecutor

The contract an operator uses to put holders' signed transfer instructions on-chain. It adds one check of its own, then hands each instruction to the token unchanged and lets the token decide.

contracts/intents/IntentExecutor.sol immutable, not a proxy admin: the main timelock not attested: a token trusts it by granting EXECUTOR_ROLE

In one minute

A holder can sign a transfer instruction, called an intent, without sending a transaction or paying gas: who receives, how much, until when, and a single-use number (the nonce). Someone else has to submit it. On an IntentToken only an account with EXECUTOR_ROLE may do that, and in the deployment that is this contract and the DvPExecutor. The bank's or relayer's keys hold OPERATOR_ROLE here and call it. The executor never holds tokens or money and never changes an intent. Its one check: it refuses any intent that says the signer is to be paid something in return, because it cannot make that payment happen. Operators can submit one intent, or a batch that settles all or nothing. The guardian can stop it at once.

How an intent is executed

The operator calls execute(token, intent, sig). The executor checks its own conditions and forwards the call. Everything about the intent itself is checked by the token, which runs the transfer through the compliance hook as an EXECUTED movement.

  1. Executor checks. The caller holds OPERATOR_ROLE (AccessControlUnauthorizedAccount), the executor is not paused (EnforcedPause), and the intent states no consideration (IntentExecutor_ConsiderationNotSupported(0)). The role check comes first. If any fails, the token is never called.
  2. Token checks. executeTransfer requires EXECUTOR_ROLE, then checks the deadline (INTENT_EXPIRED), the nonce (NONCE_USED), that a stated consideration names an executor (CONSIDERATION_NEEDS_EXECUTOR), that a named executor is the caller (WRONG_EXECUTOR), validAfter (INTENT_NOT_YET_VALID) and the signature (BAD_SIGNATURE).
  3. Policy. The movement goes through the token's pause and frozen-balance checks and its hook as EXECUTED, so the settlement window, credentials, holder restrictions, minimum position and the fund-wide holder cap all apply (One movement).
  4. Record. The token emits IntentExecuted(intentHash, from, to, amount, executor, ref), where executor is the account that called the token: this contract's address.

The constructor takes the admin and the guardian and refuses a zero address for either (IntentExecutor_ZeroAddress). It grants nothing else; operators are granted afterwards.

Why it refuses an intent that states a payment

An intent has two fields, considerationToken and considerationAmount, for what the signer is to receive in return. The holder signs them, so they appear in the message the wallet shows. The token never enforces them: it only requires that an intent stating one names the executor allowed to run it. Enforcing the payment is the named executor's job.

This executor moves one token and nothing else, so it cannot pay anyone. If it ran such an intent, the shares would move and the payment the holder read in the message would not happen. So it refuses any intent with a non-zero consideration token or amount, whoever the intent names, before calling the token. A trade with a payment goes through the DvPExecutor, which moves both sides.

The refusal holds at two layers. This executor refuses before the token is called. And the token refuses such an intent from any executor other than the one it names (WRONG_EXECUTOR), or from every executor if it names none (CONSIDERATION_NEEDS_EXECUTOR).

Batches: all or nothing

executeBatch runs the intents in array order inside one transaction. The first one that fails reverts the batch and names its position, carrying the token's revert data inside.

  • The arrays must have the same length (IntentExecutor_LengthMismatch).
  • The consideration check runs on each intent just before it is submitted. An intent that states one reverts the batch with IntentExecutor_ConsiderationNotSupported(i).
  • Intents run in order, so an earlier intent can change what a later one sees: a balance, a minimum position, or the fund's investor count.
  • A batch is for one token. Several tokens need several calls.

Checking before submitting

The executor has no pre-flight function of its own. An operator asks the token: canExecute(intent, sig) returns (ok, reason) without reverting, and runs the same checks as executeTransfer, the signature and the hook included. Call it from the executor's address (an eth_call with the executor as sender), because the executor binding compares the caller: from any other address, an intent that names this executor reads WRONG_EXECUTOR.

The token's pre-flight cannot see what belongs to the executor: OPERATOR_ROLE, the executor's pause, and the consideration refusal. It also does not check that the caller holds EXECUTOR_ROLE, so after a token revokes this executor the pre-flight still says yes and the real call fails.

Pause and recovery

The guardian pauses the executor with no delay. Pausing it stops this route only: the token itself is not paused, and the DvP executor, which holds its own EXECUTOR_ROLE on the token, keeps working. The token has its own pause for stopping every movement.

Unpausing takes the main timelock or the recovery timelock, each after its delay. The recovery timelock holds RECOVERY_ROLE here, which allows exactly two things: unpause() and revoking GUARDIAN_ROLE. It cannot grant OPERATOR_ROLE or any other role (GovernanceTimelock).

Why it is built this way

  • Forward only. The token is the single source of truth for the signature, nonce, deadline, executor binding, freeze, pause and policy. The executor checks none of them, so nothing is checked twice and the two can never disagree.
  • No funds, no state. It stores its roles and its pause flag, nothing else: no intents, no nonces, no balances.
  • Replaceable. It is a plain contract, not a proxy. Replacing it means deploying a new one and moving the token's EXECUTOR_ROLE, which is a timelock operation.
  • Operators are separate from the token. A bank or relayer key holds a role on the executor, not on the token, and the guardian can stop that route alone.
  • Refuse rather than half-settle. An intent that states a payment is refused outright, so a holder never sees shares leave without what the message promised.
