Contracts / Identity

CredentialRegistry

The record of who vouched for each address: which attester, what the address is, until when, and whether it may still send and receive. The credential rule reads it on every movement of every token.

contracts/identity/CredentialRegistry.sol immutable, not a proxy admin: the main timelock after deployment not attested: the CredentialRule that reads it is

In one minute

Before an address can receive a token, someone the issuer trusts has to vouch for it. That someone is an attester: for example the issuer's own KYC team or an outside KYC provider. The registry keeps one short record per address: which attester vouched, a set of qualification flags (identity checked, professional investor, fund, licensed institution and so on), a country code, an expiry date and a standing. It stores no names and no documents.

The main design choice is that a holder can always get out unless someone deliberately blocks them. When a record expires, or its attester is shut down, the holder can still sell or redeem but cannot receive more. Only an explicit block stops a holder from sending. The guardian can block an address or shut down an attester at once; undoing either takes a timelock, a contract that runs governance decisions only after a public delay.

How it works: a standing, worked out when asked

Each address has one stored record, and its stored status is NONE, ACTIVE, EXIT_ONLY or BLOCKED. CredentialRule never reads the stored status directly. It asks profileOf(address), which works out the standing at that moment from the stored status, the expiry, the guardian's block flag and whether the attester has been killed. That is how LAPSED exists without anyone writing it: it is an ACTIVE record whose validUntil has passed.

  1. Written as ACTIVE. An attester's set, or a signed credential submitted with register, writes the record as ACTIVE, with a validUntil in the future and only bits the attester is allowed to assert. A new write makes any record ACTIVE again, if the writer is allowed to overwrite it (see Attesters).
  2. The attester changes its own record. setStatus(address, status) sets EXIT_ONLY or BLOCKED at any time, and ACTIVE only while validUntil is still in the future (CredentialRegistry_ValidityInPast). NONE and LAPSED can never be written (CredentialRegistry_InvalidStatus).
  3. Lapsing takes no transaction. An ACTIVE record reads ACTIVE through the last second of its validUntil and LAPSED from the next one. The attester renews it with a new write.
  4. Two overrides, applied when read. A killed attester makes its records read EXIT_ONLY. A guardian block makes the address read BLOCKED whatever is stored, even an address that was never written. Neither changes the stored record, so after a revive or a cleared block the record reads as it would have without them: a record past its expiry then reads LAPSED, and a record another attester wrote over in the meantime stays theirs.

The order in which a standing is worked out

profileOf(address) returns the standing with the stored bits, country and attester id. It asks four questions in a fixed order and stops at the first yes.

What each standing allows is decided by CredentialRule, the rule that reads the registry. Other rules in a token's list can still refuse a movement this table allows.

The record

One record per address, in one storage slot. It holds flags only: no names, no evidence, no hashes of personal data. The link from an address to a person stays with the attester.

Qualification bits

The bits are named in Quals.sol. The registry never interprets them: an attester sets the bits it vouches for, and each token's policy says which it needs. Bits 8 to 15 are reserved for later shared meanings, and bits 16 to 31 are free for a deployment's own use. The names are conveniences, not legal categories. What a bit means in law is for the attester and its counsel to define.

BitNameMeant for

Attesters

An attester is an account allowed to write records, within a set of qualification bits. It is not a role: it is an entry in the registry's own list, which the main timelock manages.

  • Added in order, never reused. addAttester gives ids 0, 1, 2 and so on, for at most MAX_ATTESTERS (64) attesters, so ids 0 to 63. The list only grows, so a new attester can never take an old id and with it the records written under that id.
  • One account, one attester. The account can be a plain key or a contract account such as a multisig, which signs through ERC-1271. An account that is already an attester cannot be added again or used in a rotation (CredentialRegistry_AttesterExists).
  • Allowed bits. A write that asserts a bit outside the attester's allowedQuals reverts (CredentialRegistry_QualsNotAllowed). Changing the allowed bits does not touch records already written.
  • Who may overwrite a record. An attester may write over a record only if the address has none, the same attester wrote it, or the attester that wrote it is killed. Two providers vouching for one address therefore do not silently replace each other. Only the attester that wrote a record may change its status.
  • Killed. The guardian (with no delay) or the main timelock calls killAttester. From then on the attester's set, setStatus and signed credentials revert with CredentialRegistry_AttesterKilled, its records read EXIT_ONLY (except those that read BLOCKED), and another attester may write over them. The kill flags of all attesters share one 64-bit word, so checking both parties of a movement adds one cold storage read, not two.
  • Revived. The main timelock or the recovery timelock calls reviveAttester. It clears the kill bit and nothing else: the account and the allowed bits are as they were, and the records it still owns are resolved as if it had never been killed.

Signed credentials anyone can submit

An attester does not have to send a transaction for every holder. It can sign a credential off chain, as EIP-712 typed data, and anyone can submit it with register(credential, signature): the holder, the issuer's back office or a relayer. Whoever submits pays the gas, and the attester's key stays off the hot path.

Domain

Signature
checked against the attester's current account: ECDSA for a key, ERC-1271 for a contract account. The credential names its attester id, so the registry knows which account to ask.

register runs these checks in order:

  1. The attester id exists (CredentialRegistry_UnknownAttester) and is not killed (CredentialRegistry_AttesterKilled).
  2. issuedAt is not in the future (CredentialRegistry_IssuedInFuture).
  3. The signature is valid for the attester's account (CredentialRegistry_BadSignature).
  4. issuedAt is strictly above the issuedAt stored for the address (CredentialRegistry_StaleCredential).
  5. The same checks as set: the address is not zero, the bits are allowed, validUntil is in the future, and no other attester that is not killed owns the record. The record is then written as ACTIVE with the credential's issuedAt.

The issuedAt rule is what makes the signed path safe. A credential can be submitted once: a replay is not newer than itself. An older credential cannot undo a newer direct write or a status change, because set and setStatus both set issuedAt to the current time. An attester that wants to withdraw a credential nobody has submitted yet writes the address directly, which makes every credential issued up to that moment stale, and can then block the address with setStatus. A guardian block survives every write.

The guardian's block

The guardian is a multisig whose powers can only stop things. Here it holds GUARDIAN_ROLE and can do two things, both at once, with no delay: block an address (blockSubject) and kill an attester (killAttester).

  • A block is a separate flag on the record, not a status. It works on an address that was never written, so a later write is born blocked.
  • No attester can lift it: set and register keep the flag, and setStatus(ACTIVE) changes only the stored status underneath it.
  • Only clearGuardianBlock lifts it, called by the main timelock (DEFAULT_ADMIN_ROLE) or the recovery timelock (RECOVERY_ROLE), both after their delay.
  • The recovery timelock is needed because the guardian can cancel operations on the main timelock, and could therefore cancel its own unblock there. Nobody can cancel on the recovery timelock. For the same reason the recovery timelock may revive an attester and remove the guardian (revokeRole(GUARDIAN_ROLE, …)), and nothing else.

The post-deployment check pins the result: one attester, not killed; the guardian holds only GUARDIAN_ROLE; the recovery timelock holds only RECOVERY_ROLE.

isVerified

The registry also answers isVerified(address) from IIdentityRegistry, the one-question view that an identity registry such as ERC-3643's offers. It is true only when the standing is ACTIVE. No contract in the deployment calls it. CredentialRule reads profileOf instead, because a yes-or-no answer cannot tell a holder who may still leave (EXIT_ONLY, LAPSED) from one who may not (BLOCKED, NONE). The registry reports both interfaces through ERC-165.

If an attester is compromised

The registry trusts an attester's call or signature. It holds no proof that the KYC behind a record took place: no documents, no names, no hashes of personal data. Whoever controls an attester's key can therefore do everything that attester can do, until it is stopped.

What it can write

  • ACTIVE records, directly or as signed credentials anyone can submit, for any address that has no record, whose record it wrote itself, or whose attester is killed. It chooses the expiry and the country.
  • Only bits within its own allowedQuals.
  • A new status on the records it wrote: EXIT_ONLY or BLOCKED, which stops those holders receiving or, for BLOCKED, sending; or ACTIVE again while the record is valid.

What limits it

  • The bits it may assert. Set by the main timelock; any other bit reverts with CredentialRegistry_QualsNotAllowed.
  • Each token's trusted-attester bitmap. A token whose policy does not list the attester's id admits none of its records as a receiver.
  • Other attesters' records. It cannot overwrite or change a record another attester wrote while that attester is not killed.
  • The guardian. killAttester stops it at once, and blockSubject stops any address it vouched for. It cannot clear a guardian block.

After a kill, the holders it vouched for read EXIT_ONLY: they can leave, and cannot receive. Holders it had set to BLOCKED stay BLOCKED, because a stored block beats a kill. Another attester can write over any of its records, and the agent's forcedTransfer and a burn by a BURNER_ROLE holder still work on a blocked holder. Then the main timelock rotates the attester's account with setAttesterAccount, which makes every signature by the old key fail. reviveAttester changes nothing but the kill flag, so the account is rotated before the attester is revived.

The bitmap applies to receivers. The sender check of CredentialRule reads only the standing, not which attester wrote the record, so that an existing holder can always leave.

Why it is built this way

  • Flags stored, standing worked out on read. Expiry, kills and blocks are applied by profileOf, so the rule does no time or trust arithmetic and an expiry needs no transaction. Three invariant tests hold this together: issuedAt never goes down, an address that reads ACTIVE is within its validity, and a guardian block always reads BLOCKED.
  • Getting out is the default. A lapsed record and a killed attester both leave the holder able to sell, burn and redeem. Only an explicit block, by the attester or the guardian, stops a holder from sending.
  • The guardian can only stop. It blocks and kills with no delay; lifting a block and reviving an attester go through a timelock. The recovery timelock exists so that the guardian cannot keep its own block in place by cancelling the unblock.
  • Ids are never reused. A killed attester's records cannot come back to life under a new attester that happens to get the same id.
  • Not a proxy. The registry cannot be upgraded. A change to the record's layout means a new registry, a new rule that reads it, and a setRules on each token.
  • Not attested itself. The council attests CredentialRule, whose code hash covers the registry's address as an immutable but not the registry's code. The council reads the registry's code, admin and attester list before it attests the rule.
  • No personal data. No field and no event carries a name or evidence. The flags themselves are public on chain, and a country or a qualification bit can still say something about a customer.
