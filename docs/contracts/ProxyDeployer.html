Contracts / Deployment

ProxyDeployer

Creates every token. It puts each one at an address anyone can work out in advance, sets it up in the same transaction, and refuses to finish unless the token came up exactly as the security council reviewed it.

contracts/deploy/ProxyDeployer.sol immutable, not a proxy owner: the main timelock after deployment not attested: nothing installs it by code hash

In one minute

A token here is a small proxy contract that points at shared, reviewed code (its implementation). Anyone could deploy such a proxy. What makes a token one of ours is how it was placed: only through this contract, only by its owner, and only if five things check out. The code behind it is reviewed, the token uses the same registry of reviewed code, it uses the shared compliance hook named in the call, that hook holds the exact list of rules the call expected, and the token's symbol is the one its address was computed from. If any check fails, nothing is created and the symbol stays free.

How a token is placed

The owner calls deploy(symbol, implementation, initData, hook, expectedRules). The steps run in this order, and any failure undoes the whole call, including the step that marked the symbol as used.

  1. One symbol, one token. The symbol's hash is the CREATE2 salt, and each salt can be used once, with any implementation (ProxyDeployer_SaltUsed(salt)).
  2. Reviewed code only. Before any proxy exists, the deployer asks its registry whether the implementation's code hash is attested as IMPLEMENTATION (ProxyDeployer_ImplementationNotAttested(implementation)). This check has to live here: the token's own setup function is the implementation's code, so code nobody reviewed would simply skip a check of its own.
  3. Set up in the same transaction. The proxy is created without setup data, then the deployer calls it with initData right away. Nobody can get in between and set it up first.
  4. Read back and compare. The token must name the deployer's registry (ProxyDeployer_RegistryMismatch(expected, actual)), its hook must be the hook argument (ProxyDeployer_HookNotInstalled(expected, installed)), the hook must hold exactly expectedRules for it, same length and same order (ProxyDeployer_RulesMismatch(hook, proxy)), and the token must report the symbol the salt came from (ProxyDeployer_SymbolMismatch(expected, actual)).

The address is known before the token exists

The token's address depends on three things only: this deployer's own address, the token's symbol, and the implementation. It does not depend on the setup data, which carries the admin, the guardian, the hook and the rules. So the address can be computed, published and monitored before anything is deployed, and changing an admin or a rule in the plan does not move the token.

predict(symbol, implementation) returns the address. It is CREATE2 with salt keccak256(bytes(symbol)) over the creation code of TokenProxy with arguments (implementation, ""), the same formula anyone can run off-chain.

Why it is built this way

  • Only the owner can deploy. The address does not cover the setup data, so without the gate anyone could take a token's address first, with the same symbol and implementation but their own admin. The deployer account owns it while the system is set up, and the deployment hands ownership to the main timelock, so every later token goes through governance and its delay.
  • The registry is fixed at construction. The constructor takes the owner and the registry and refuses a zero registry (ProxyDeployer_ZeroAddress). There is no setter, so no one can point the deployer at a different list of reviewed code.
  • The registry is read when the token is placed, not later. Like the other places that ask the registry, a later withdrawal of an attestation does not touch a token that already exists.
  • It holds no roles and no funds. After the setup call it has no power over the token it created.

What it does not check

  • It compares the token with the hook and the rule list passed in the call. It does not know which hook instance the council reviewed, or the deployment's intended rule order. The post-deployment check does that (Deployment and governance).
  • It is not itself attested: nothing installs it by code hash. The council checks its code against the release build like any other deployed contract.
