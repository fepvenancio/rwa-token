Contracts / Token

IntentToken

The plain gated token: an ERC-20 whose every movement passes the compliance hook, and whose holders can also settle by signed intent. It adds almost nothing of its own: a setup function and the name of its template.

contracts/tokens/IntentToken.sol upgradeable: UUPS, behind a TokenProxy admin: the main timelock implementation attested as IMPLEMENTATION

In one minute

This is the template for a permissioned token that changes hands between verified holders. Everything it does comes from two shared pieces: the base, which keeps balances and roles, gives the issuer its enforcement tools and asks the compliance hook about every movement, and the intent mixin, which lets a holder sign a transfer that an approved executor settles later.

The deployment creates one, called "Intent Token" with the symbol INT unless the deployment parameters say otherwise. It is placed through ProxyDeployer with five rules in a fixed order, configured, given its roles, and then handed to the main timelock, so every later change goes through governance and its delay.

What the token is made of

The token's address is a proxy: a small contract that holds all the state (balances, roles, frozen amounts, used intent nonces) and runs the shared implementation code for every call. That code is three layers on top of OpenZeppelin. Every movement, whatever its kind, asks the one shared hook, which runs this token's rules in order and stops at the first refusal.

  1. TokenProxy is OpenZeppelin's ERC-1967 proxy. Its address follows from ProxyDeployer's address, the symbol and the implementation, so it is known before deployment. Changing the code behind it is a governance upgrade.
  2. IntentToken itself adds only initialize and templateId, and a constructor that locks the implementation so only proxies can be set up.
  3. IntentSettledUpgradeable adds signed intents, settled by an executor as EXECUTED.
  4. PolicyGatedERC20Upgradeable adds everything else: ERC-20, roles, mint, burn, forced transfer, frozen amounts, pause, permit, multicall, upgrades, and the single movement path that asks the hook.

Its rules, in order

The deployment fixes each token's list in RULE_ORDER (ignition/modules/roles.ts). For the intent token it is five rules. The credential check comes first, and the minimum position right after it, so that when a minimum is set the rules that follow judge real positions rather than dust. The settlement window is in this list only: the vaults have no executed intents to time. The fund's cap comes last.

The first four rules keep their settings per token and accept a change only from an account that holds the right role on this token: DEFAULT_ADMIN_ROLE for policy settings, AGENT_ROLE for a holder's lockup or freeze. The investor cap is a setting of the Fund, which the main timelock owns. Until the credential policy is set, the credential rule admits no receiver; until the fund registers the token, the fund rule refuses every movement. So no balance can exist before the token is configured.

Who deploys it

Two Ignition modules build the deployment. Components deploys the shared pieces, including one IntentToken implementation; the security council then attests the rules, the hook and the implementations; then Activate creates and sets up the token itself. While Activate runs, the deployer account is the token's admin; at the end it gives that up.

  1. Place. The deployer calls ProxyDeployer.deploy(symbol, implementation, initData, hook, rules), where initData is the initialize call with the token's name and symbol, the deployer as admin, the guardian, the registry, the shared hook and the rule list from RULE_ORDER.intent. ProxyDeployer refuses an implementation the council has not attested, and finishes only if the token names its registry, uses the given hook, and the hook holds exactly those rules in that order. See ProxyDeployer.
  2. Configure. While the deployer is still the token's admin, it sets the credential policy, the settlement window and the minimum position, and the fund registers the token as a class.
  3. Grant roles. The intent token is the only token in the deployment with a minter and a burner. Its EXECUTOR_ROLE goes to the two executor contracts and to no one else, so every signed intent is submitted through one of them. The guardian already holds GUARDIAN_ROLE from initialize.
  4. Hand over. The main timelock receives DEFAULT_ADMIN_ROLE and the deployer renounces its own. From then on, a new token, a change to the rule list, a role change or an upgrade is a timelock operation.

Outside these modules, the KYC attester has to issue a credential to every holder before anyone can receive the token.

Why it is built this way

  • A template is a name and a setup function. All behaviour lives in the shared base and the mixin, so every template behaves the same where they overlap, and a fix in the base reaches every template through its own reviewed upgrade.
  • The template id keeps a token on its own code. An attestation says the code has been reviewed; templateId() says what it is for. An upgrade of this token to an attested vault implementation is refused with Templated_WrongTemplate.
  • Live with its policy from the first block. The rules are installed by initialize in the transaction that creates the proxy, and ProxyDeployer checks the result in that same transaction, so there is no moment when the token exists without its rules.
  • Each implementation deployment needs its own attestation. UUPS code records its own address, so two deployments of the same source have different code hashes, and the council attests each one it allows.
