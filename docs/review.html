Security review

What has been reviewed, by whom and when, what came out of it, and what has not been looked at. Two reviews are recorded here in detail. The first was run by an AI assistant, the repository does not record who ran the second, neither is an audit, and this page is a record, not a certification.

In one minute

Two reviews in the last week of October 2026 are recorded here in detail, each on the code as it stood then. The review of 2026-10-26, by an AI assistant, covered the token, its policy and the contracts around them, and left out the vaults and the credential layer. It rated nothing medium or higher. The review of 2026-10-26: how it worked

This account comes from the first committed version of this page (git show df4f13a:docs/review.html). Nothing else in the repository records how the review ran, so it cannot be checked.

  1. A read by the assistant of every contract in scope, against the project's build brief, the documentation and SECURITY.md.
  2. Four parallel scans of the code against a catalogue of 170 known attack patterns. Each pattern was marked skipped, surviving or borderline, and each survivor was traced from its external entry point through every modifier and guard.
  3. One adversarial pass that reasoned freely about the code and tried to build a concrete attack.
  4. The full test suite, npx hardhat test, at 1011 passing (915 Solidity, 96 Node) at that commit, as PLAN.md records. The Halmos properties were read and not re-run.
  5. Every candidate finding was checked against the code and the repository's own notes before it was reported.

The review was run by an AI assistant, and its scan reports are not stored in the repository. An AI review cannot show that no bug exists. This page does not replace an external audit, and none has happened.

Finding 1: the deployer checks the implementation

deploy(symbol, implementation, initData, hook, expectedRules) asks its registry, before it creates the proxy, whether the implementation's code hash is attested as IMPLEMENTATION. The check has to sit in the deployer: the token's own setup function is the implementation's code, so unreviewed code would simply skip a check of its own. After setup the deployer also requires the token to name the deployer's own registry, because a token on another registry could have its own hook and rules attested there.

The registry is fixed when the deployer is created and cannot be changed. The tests are in ProxyDeployer.t.sol. deploy is owner-only, and after CoreHandover the owner is the operations account, so a launch has no timelock delay. A stolen operations key can still place a token over attested code with its own admin, and can use up a symbol. It cannot change an existing product.

Finding 2: a batch is all-or-nothing

executeBatch runs every intent in one transaction. If one fails, the executor reverts with IntentExecutor_BatchItemFailed(index, reason), carrying the token's own revert data, and nothing in the batch settles. An intent that states a payment is refused first with IntentExecutor_ConsiderationNotSupported(index). So any signer in the batch can make it fail, by cancelling the nonce with cancelIntent or by moving the balance first. Nobody loses tokens: the cost is the operator's gas and time.

This is by design. The operator can pre-flight each intent with canExecute(intent, sig, executor), naming the executor's address, submit intents one at a time with execute, or drop the failing intent and send the rest again.

Pinned by test_WhenOneIntentIsRejected_NothingSettlesAndTheIndexIsReported, test_WhenOneIntentFails_ItRevertsWithItsIndexAndTheTokensReason and test_WhenTheFailingIntentIsDroppedAndResubmitted_TheRestSettles in IntentExecutor.t.sol.

Finding 3: dust and the investor slot

FundHoldersRule counts an address as an investor as soon as it holds any amount of a class. With no minimum position, one unit is enough. Someone with several addresses that hold an eligible credential can send each of them one unit, fill the fund's cap, and keep new investors out until the agent takes the dust back with a forced transfer.

MinPositionRule closes this where a token lists it with a minimum above 0. It refuses with BELOW_MIN_POSITION a transfer, intent or mint that would leave the receiver above zero and below the minimum, and a movement that would leave the sender such a remainder. Forced moves, the burner's burns, the token itself and accounts the token's admin exempts are outside the rule, so the agent can still clear dust.

It is not on by default. The demo profile full lists the rule second on each of its tokens, with the minimum taken from the minPosition parameter of Product.ts, which is 0 unless given. The other profiles list neither this rule nor FundHoldersRule. On a fund class with no minimum the finding stands, and the answer is operational: the agent's forced transfer, and monitoring of the investor count.

Pinned by test_WhenADustTransferTargetsAnEmptyAccount_ItIsRejectedWithParity, test_WhenATransferWouldLeaveDustBehind_ItIsRejected, test_WhenAMintWouldLeaveDust_ItIsRejected and test_WhenForced_DustIsAllowed in RuleSetIntegration.t.sol.

What that review's adversarial pass tried and could not break

The first committed version of this page (df4f13a) lists these as what the pass tried, and nothing else in the repository records them. Each sentence below was read again against this commit. That the code still reads this way is not a new review of it.

  • Shared hook and rule state. An address can set the rule list of its own address. Anyone else needs DEFAULT_ADMIN_ROLE on that token, and naming an address with no code reverts. afterTransfer is accepted from the token it names and no other caller. A fake token that names itself writes under its own key, and FundHoldersRule rejects a token that is not a registered class of its fund.
  • Copies of attested contracts. A hook or rule deployed again from the same code with the same constructor arguments has the same attested hash. It behaves the same and starts with empty state. Installing it on a token needs the token's admin, which after hand-over is the timelock.
  • The intent path. The checks run in the documented order, the type hash matches the struct, and the nonce is marked used before the tokens move. Signatures go through OpenZeppelin's SignatureChecker: ECDSA accepts low-s signatures only, and smart accounts (ERC-1271) are asked with a read-only call.
  • Trade settlement. The mirror check ties the two legs of a DvP trade together. In the ERC-3009 form the buyer's authorization nonce is keccak256(abi.encode(securityToken, intentHash)), which commits to the security token's address and the seller's intent. Both entry points are guarded against reentry. In the ERC-3009 form the executor also checks that its own cash balance ends where it started and that the seller's rises by exactly the price.
  • Frozen balances. The release of frozen tokens cannot underflow: _releaseFrozen reverts above the balance, so the frozen part an enforcement action takes is at most the frozen amount.
  • Governance and deployment. The recovery role is narrow, the guardian can stop things and do little else, and the registry refuses to attest the hash of empty code.

After the sixteen. The last check of these pages found that exitOnly() read true through a read of nothing and false again when the value returned, although no count had been made. No money was at risk, because dealing is stopped through such a read either way. It is fixed in pull request 22.

What stays open. A read that is low and not nothing still counts at once, and recovers at maxRate. A fall of half or less in one count leaves deposits open at that price, and falls with a count between them do not add up. A real loss of that size, later made good, needs no wrong read: the buyer shares the recovery.

During a read of nothing, a donation that lifts the priced value above feesOwed makes it a low read. In a run, a stranger's one unit took a holder's 1,000 to one raw unit of the asset (a millionth of a token with 6 decimals), and it was still one a year after the target got its money back at a limit of 10%. The stranger cannot buy shares from the vault at that price, because deposits close at that count, and the timelock has to raise the rate to bring the value back. A donation of half the counted value or more does not close them: in a run, 500 donated and 100,000 deposited during a read of nothing took the holder's 1,000 to about 505 once the target had recovered, and left the depositor about 495 ahead. The donations need a target that reads nothing while it is still fresh, and the council's reading of each target before attesting it is the control. New money after a close needs a new vault.

Behaviour that looks like a bug and is on purpose

These behaviours are in the code by design. They are listed so that a reader does not report them as findings. SECURITY.md section 3 has the longer list, vaults and legos included.

  • canTransfer can say yes where the write reverts. ERC-7943 forbids it to fail on a plain balance shortfall, so with nothing frozen an amount above the balance reads true when the rules accept it. canTransferWithReason says no with INSUFFICIENT_UNFROZEN.
  • A pause stops mints and burns too. Only FORCED movements pass.
  • The account questions are not movement answers. canSend and canReceive leave out the fund's investor cap and the minimum position, which ERC-7943 keeps out of them. They also cannot see the kinds a rule exempts: canSend says no for a locked holder whose forced transfer still passes, and for a locked holder that holds BURNER_ROLE, whose own burn reads true in canTransfer.
  • Revoking an attestation does not affect running tokens. The registry is asked at install and upgrade time. The guardian can pause while governance removes the component.
  • One unit can still reach an existing holder. A minimum does not stop one unit sent to a holder at or above it. That holder's exit of its old exact balance then leaves a remainder and reverts with BELOW_MIN_POSITION; it exits its current balance instead.
  • Lowering the fund's cap is a ratchet. While the investor count is above the cap, no new investor gets in, not even by a move that empties the sender's only class. Existing investors can still move among themselves and leave (test_WhenTheCountIsAboveALoweredCap_ANetZeroMoveIsStillRejected).
  • The investor count is by address. One person with two addresses counts twice.
  • A burner's own burns are enforcement burns. The rules look at the operator, so a burn by a BURNER_ROLE holder passes its own lockup and minimum position. A burner account should not also be used as an investor.
  • The recovery timelock administers itself, as every OpenZeppelin TimelockController does: an operation it runs, after its delay, can change its own roles. The floor on its delay still holds.
  • With no shares a report changes nothing. A desk proposes a value of zero whatever is reported or sits in the portfolio, and a 4626 counts zero, so the next investors buy at par. What is left goes to them.
  • A low read counts at once. Losses are not rate limited. Deposits stay open at a price that can still be read while the fall in one count is half or less, and close for good beyond that. See what checking these pages found.
  • Pre-flights answer for the latest block. A write lands in a later one, so at a lockup end, a window edge or an intent deadline the two can differ by a second.
