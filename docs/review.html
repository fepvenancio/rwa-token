Security review

On 2026-10-26 the token, its policy contracts, the registry, the main timelock, the fund, the deployer and the two executors were reviewed for security. The review found no issue it could rate medium or higher. This page sets out what it covered, how it worked, what it found and where each item stands, and the tests that hold the properties it relied on.

reviewed 2026-10-26 nothing rated medium or higher 1 low finding, fixed not a certification

In one minute

A reviewer read the token, its policy and the contracts around it, ran a scan against a catalogue of known attack patterns, and then tried freely to build an attack. Nothing rated medium or higher came out of it. One low finding concerns the deployer, which must ask the registry of reviewed code about a new token's implementation; it does (finding 1). Two informational items are by design or depend on configuration: a batch of intents is all-or-nothing, and while a token's minimum position is 0, tiny transfers can take investor slots. The identity contracts and the vaults were not part of the review.

Scope

The review covered PolicyGatedERC20Upgradeable and IntentToken and the policy, fund, governance, deployment and settlement contracts around them. The identity layer (CredentialRegistry, CredentialRule) and the two vaults were not part of it.

The code here. This page describes the reviewed contracts at commit 2f8c2e7, which includes the fix for finding 1 below in ProxyDeployer. The test names on this page are the ones at that commit.

How the review worked

  1. A manual read of every contract in scope, against the project's build brief, the documentation and SECURITY.md.
  2. Four parallel scans of the code against a catalogue of 170 known attack patterns. Each pattern was marked skipped, surviving or borderline, and each survivor was traced from its external entry point through every modifier and guard.
  3. One adversarial pass that reasoned freely about the code and tried to build a concrete attack.
  4. The full test suite, npx hardhat test (Solidity unit, fuzz and invariant tests, and Node tests with viem). The Halmos symbolic properties run in CI on every pull request and on pushes to main (npm run test:halmos); they were read for the review, not re-run.
  5. Every candidate finding was checked against the code and the repository's own notes before it was reported.

The review was run by an AI assistant, and its scan reports are not stored in the repository. An AI review cannot show that no bug exists. Mutation testing, the Halmos properties and an external audit are stronger evidence than this page, and this page does not replace them.

Findings

Each was checked against the code. None puts funds at risk.

Finding 1: the deployer checks the implementation

deploy(symbol, implementation, initData, hook, expectedRules) asks its registry, before it creates the proxy, whether the implementation's code hash is attested as IMPLEMENTATION. The check has to sit in the deployer: the token's own setup function is the implementation's code, so unreviewed code would simply skip a check of its own. After setup the deployer also requires the token to name the deployer's own registry, because a token on another registry could have its own hook and rules attested there.

Finding 2: a batch is all-or-nothing

executeBatch runs every intent in one transaction. If one fails, the executor reverts with IntentExecutor_BatchItemFailed(index, reason), carrying the token's own revert data, and nothing in the batch settles. So any signer in the batch can make it fail, by cancelling the nonce with cancelIntent or by moving the balance first. Nobody loses tokens: the cost is the operator's gas and time.

This is by design. The operator can pre-flight each intent with canExecute, called from the executor's address, submit intents one at a time with execute, or drop the failing intent and send the rest again.

Pinned by test_WhenOneIntentIsRejected_NothingSettlesAndTheIndexIsReported, test_WhenOneIntentFails_ItRevertsWithItsIndexAndTheTokensReason and test_WhenTheFailingIntentIsDroppedAndResubmitted_TheRestSettles in IntentExecutor.t.sol.

Finding 3: dust and the investor slot

FundHoldersRule counts an address as an investor as soon as it holds any amount of a class. With no minimum position, one unit is enough. Someone with several addresses that hold an eligible credential can send each of them one unit, fill the fund's cap, and keep new investors out until the agent takes the dust back with a forced transfer.

MinPositionRule closes this where the token has a minimum above 0. It sits second in every deployed rule list, before FundHoldersRule, and refuses with BELOW_MIN_POSITION any transfer, intent or mint that would leave the receiver above zero and below the minimum, and any movement that would leave the sender such a remainder. The rules after it therefore see only real positions. Forced moves, the burner's burns, the token itself and accounts the token's admin exempts are outside the rule, so the agent can still clear dust.

The deployment sets each token's minimum from a parameter (intentMinPosition, fundMinPosition, asyncFundMinPosition), which is 0 by default. Until a minimum is set the rule is off and the finding stands; the operational answer is then the agent's forced transfer and monitoring of the investor count.

Pinned by test_WhenADustTransferTargetsAnEmptyAccount_ItIsRejectedWithParity, test_WhenATransferWouldLeaveDustBehind_ItIsRejected, test_WhenAMintWouldLeaveDust_ItIsRejected and test_WhenForced_DustIsAllowed in RuleSetIntegration.t.sol.

What the adversarial pass tried and could not break

  • Shared hook and rule state. An address can set the rule list of its own address only. Anyone else needs DEFAULT_ADMIN_ROLE on that token, and an address with no code is refused. afterTransfer is accepted only from the token it names. A fake token that names itself can only write under its own key, and FundHoldersRule rejects a token that is not a registered class of its fund.
  • Copies of attested contracts. A hook or rule deployed again from the same code has the same attested hash. It behaves the same, starts with empty state, and installing it on a token needs the timelock.
  • The intent path. The checks run in the documented order, the type hash matches the struct, the nonce is marked used before the tokens move, and a revert also undoes the announced kind. Signatures go through OpenZeppelin's SignatureChecker: ECDSA accepts low-s signatures only, and smart accounts (ERC-1271) are asked with a read-only call.
  • Trade settlement. The mirror check ties the two legs of a DvP trade together. In the ERC-3009 form the buyer's authorization nonce is keccak256(abi.encode(securityToken, intentHash)), which commits to the security token's address and the seller's intent. Both entry points are guarded against reentry. In the ERC-3009 form the executor also checks that its own cash balance ends where it started and that the seller's rises by exactly the price.
  • Frozen balances. The release of frozen tokens cannot underflow: an enforcement action never takes more than the balance, so the frozen part it takes is never more than the frozen amount.
  • Governance and deployment. The recovery role is narrow, the guardian can only stop things, and the registry refuses to attest the hash of empty code.

Behaviour that looks like a bug and is on purpose

These behaviours are in the code by design. They are listed so that a reader does not report them as findings.

  • canTransfer can say yes where the write reverts. ERC-7943 forbids it to fail on a plain balance shortfall, so with nothing frozen an amount above the balance reads true when the rules accept it. canTransferWithReason says no with INSUFFICIENT_UNFROZEN.
  • A pause stops mints and burns too. Only FORCED movements pass.
  • The account questions are not movement answers. canSend and canReceive leave out the fund's investor cap and the minimum position, which ERC-7943 keeps out of them. They also cannot see the kinds a rule exempts: canSend says LOCKED for a locked holder whose forced transfer still passes, and for a locked holder that holds BURNER_ROLE, whose own burn reads true in canTransfer.
  • Revoking an attestation does not affect running tokens. The registry is asked at install and upgrade time only. The guardian can pause while governance removes the component.
  • One unit can still reach an existing holder. A minimum does not stop one unit sent to a holder at or above it. That holder's exit of its old exact balance then leaves a remainder and reverts with BELOW_MIN_POSITION; it exits its current balance instead.
  • Lowering the fund's cap is a ratchet. While the investor count is above the cap, no new investor gets in, not even by a move that empties the sender's only class. Existing investors can still move among themselves and leave (test_WhenTheCountIsAboveALoweredCap_ANetZeroMoveIsStillRejected).
  • The investor count is by address. One person with two addresses counts twice.
  • A burner's own burns are enforcement burns. The rules look at the operator, so a burn by a BURNER_ROLE holder passes its own lockup and minimum position. A burner account should not also be used as an investor.
  • The recovery timelock administers itself, as every OpenZeppelin TimelockController does: an operation it runs, after its delay, can change its own roles.
  • Pre-flights answer for the latest block. A write lands in a later one, so at a lockup end, a window edge or an intent deadline the two can differ by a second.

What the review does not cover

  • CredentialRegistry and CredentialRule, the identity layer that decides who may hold.
  • Gated4626Vault and Gated7540Vault, and everything only they use.
  • The Ignition deployment modules in ignition/modules/.
  • OpenZeppelin 5.6.1 itself. The contracts were read for how they use it, not the library.
  • Economic and governance risk. A compromised security council, governance multisig or issuer key is outside what the code can defend against.
