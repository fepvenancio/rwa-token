Overview / Governance

Deployment and governance

The system goes live in two scripted stages with a security review between them, and ends with every admin power in the hands of a timelock. After that, every change to the code, the hook, the rule lists, the policy parameters or the roles takes the same public, delayed path, and an incident follows a fixed order: stop, enforce, resume.

In one minute

Deployment uses Hardhat Ignition, a tool that runs a scripted list of contract deployments and calls. The first script, Components, deploys everything that does not depend on a token. Then the security council reviews that code and attests it: it records each contract's code fingerprint (its codehash) in the PolicyRegistry, the list of reviewed code. The second script, Activate, creates the tokens, configures them and hands the deployer's admin powers to the main timelock, except on the two timelocks, which administer themselves; along the way it refuses any implementation, hook or rule that is not on that list. From then on a change is proposed by governance, waits at least seven days in public, and runs only if nobody cancels it.

Going live

Five steps, by four parties. The test fixture deployStack in test/nodejs/fixtures.ts runs this exact sequence on a local chain, playing the council and the KYC attester, so every test starts from a real deployment.

The council step

The council attests five rules as RULE, the hook as HOOK and the three implementations as IMPLEMENTATION, with a link to its review for each (attest(codehash, kind, uri)). The README describes the procedure: rebuild from the release tag with npm run verify:reproducible, compare with the published build and with the code on chain, then attest.

A codehash covers a contract's code including its immutable values, such as an address fixed at construction, but not the code that lives at that address. So the council also reads what three contracts point at:

  • the hook's REGISTRY(), which must be the deployment's registry;
  • the credential registry behind CredentialRule: its code, its admin and its attester list;
  • the fund behind FundHoldersRule: its code and its owner.

Every deployment of a UUPS implementation has its own codehash, because OpenZeppelin's UUPSUpgradeable stores the implementation's own address as an immutable. A redeployed hook or rule with the same constructor arguments, on the other hand, shares the codehash of the attested one, and attest refuses a second attestation of it (PolicyRegistry_AlreadyAttested).

Stage 2: Activate

Activate takes the addresses from stage 1 as parameters, plus the accounts that will hold the operational roles (minter, burner, agent, operator, fulfiller, kycAttester), the vaults' asset and the 7540 vault's custody, the settlement window (windowOpen, windowClose, windowDays), the fund's fundHolderCap and each token's minimum position (0 by default, which switches the rule off). Ignition orders the calls by what each one depends on.

Each token's rules

RULE_ORDER in ignition/modules/roles.ts is the ordered list each token installs. The hook asks the rules in this order and stops at the first rejection. The symbols and names are defaults that the <key>Symbol and <key>Name parameters can override; the CREATE2 salt is the hash of the symbol, so the symbol, with the implementation, decides the token's address.

The hand-over

Until the hand-over, the deployer administers the tokens, both executors, the credential registry and both timelocks, and owns ProxyDeployer and the fund. The hand-over moves the powers over the tokens, both executors, the credential registry, ProxyDeployer and the fund to the main timelock, and removes the deployer. Each timelock administers itself, as OpenZeppelin sets up every TimelockController, so on the timelocks the deployer only renounces. On the recovery timelock it also revokes the canceller role that OpenZeppelin gives governance as a proposer, so nobody can cancel there. Who can do what lists every holder afterwards.

The post-deploy check

assertHandedOver in test/nodejs/fixtures.ts runs after every fixture deployment and is the check to run after a live one. It reads the chain only. It asserts that:

  1. the deployer holds no role on either timelock, either registry, the tokens or the executors, and the main timelock holds DEFAULT_ADMIN_ROLE on itself, both registries, the tokens and the executors;
  2. the recovery timelock holds exactly RECOVERY_ROLE on the main timelock, each token, both executors and the credential registry, nothing on the policy registry; no account the deployment knows of can cancel there, and the guardian holds nothing on it;
  3. EXECUTOR_ROLE on IntentToken is held by the two executors and by no account the deployment knows of; the main timelock holds UPGRADER_ROLE on each token and no known account does; the DvP executor's operator and guardian are the deployment's;
  4. every token runs the exact hook instance the council reviewed, that hook names the registry, and its list for each token equals RULE_ORDER; no rule has access control of its own;
  5. ProxyDeployer and the fund are owned by the main timelock; the fund runs the attested rule that points back at it, has the intended cap, and holds the three tokens as classes 1 to 3, each intact (firstBrokenClass() is the zero address);
  6. the guardian holds only GUARDIAN_ROLE on the credential registry, which has one attester, the KYC provider, not killed; the credential rule reads that registry and is attested; each token's policy is KYC from attester 0;
  7. the guardian can cancel on the main timelock but cannot propose or execute, and both delays are at least seven days.

Item 4 covers what attestation cannot. A second ComplianceHook on the same registry has the same codehash, so it is attested too and ProxyDeployer accepts it. A test deploys such a twin: Activate completes on it, and the check refuses it with "runs another hook".

Changing the policy later

After the hand-over every change takes one path through the main timelock. What differs is the call at the end and the check that guards it.

Replace a token's rule list

hook.setRules(token, rules) replaces the whole ordered list of one token in one call and leaves every other token alone. The caller must be the token itself or hold DEFAULT_ADMIN_ROLE on it, which the hook asks the token at call time (ComplianceHook_NotTokenAdmin). Each rule must be attested as RULE (ComplianceHook_NotAttested), at most 16 (ComplianceHook_TooManyRules), and no two may share a ruleId (ComplianceHook_DuplicateRule). Any failure keeps the old list. An empty list is accepted and rejects every movement with NO_RULES. The hook emits RuleSetChanged(token, ruleIds).

Two things to avoid. Dropping CredentialRule without an equivalent: no other shipped rule checks who the holder is, and the hook does not warn. Dropping FundHoldersRule from a class that has holders: the fund stops hearing about that class's movements and its investor count goes stale. To have a new minimum in force from the moment MinPositionRule is listed, put setMinPosition before setRules in the same batch.

Replace the hook

One hook serves every token, and each token moves by its own setPolicyHook. A new ComplianceHook(registry) on the same registry has the attested codehash already, so it needs no new attestation. The batch sets each moving token's list on the new hook first, called by the timelock as the token's admin, then calls token.setPolicyHook(newHook). In that order, because a token whose new hook holds no list for it rejects every movement with NO_RULES. setPolicyHook checks that the hook is attested as HOOK (PolicyGated_NotAttested) and names the token's registry (PolicyGated_HookRegistryMismatch), and emits PolicyHookChanged. The rules need no change: they accept after_ from whichever hook the token reports. A fund class's new list must still name the fund's current rule.

Change the fund's rule

The investor count and each investor's classes live in Fund, not in the rule, so a new rule starts with the right numbers. What changes is who may write them: after fund.setRule(newRule), only newRule may call join and leave. A class whose list still names the old rule is closed: the old rule sees that it is not the installed one and rejects every movement of that class with NOT_FUND_CLASS, forced ones included. So the change is one batch: fund.setRule(newRule) and, for every registered class, hook.setRules(class, list) with the old rule swapped for the new one. setRule requires the new rule to be attested as RULE (Fund_NotAttested).

Upgrade a token

Deploy the new implementation; the council attests it as IMPLEMENTATION; governance schedules token.upgradeToAndCall(newImplementation, data). _authorizeUpgrade requires UPGRADER_ROLE (the main timelock), the attestation, and that the new implementation reports the token's own templateId(), so an attested vault implementation offered to an IntentToken proxy is refused with Templated_WrongTemplate. The template ids are keccak256 of the template's name and carry no version. State lives in ERC-7201 namespaced storage, so new code keeps reading the old fields; npm run validate:upgrades runs OpenZeppelin's upgrade-safety check.

Add a token

Governance schedules proxyDeployer.deploy(symbol, implementation, initData, hook, rules), with initData naming the main timelock as admin. ProxyDeployer.predict(symbol, implementation) gives the address in advance. The token comes up with its admin and guardian only, so the operation also needs its other roles (an agent, UPGRADER_ROLE and RECOVERY_ROLE among them), its credential policy, since until setPolicy its credential rule admits no receiver, and, to join the fund, fund.registerClass(token) while its supply is still zero and its list names the fund's rule. A new implementation needs the council's attestation first.

Settings and roles

Credential policy, settlement window, minimum position and its exemptions are set on the rules by the token's admin. The fund's cap and exemptions, custody of the 7540 vault, the credential registry's attesters and every role change are called by the main timelock too. Among the policy inputs, the agent's lockups and address freezes on HolderRestrictionRule, the KYC attester's credentials, and the guardian's blocks and attester kills on the credential registry take effect at once.

Watching the policy

The hook accepts any list of attested rules, and Fund.setRule does not look at the classes. So a list could leave out the fund's rule, or the fund's rule could change under lists that still name the old one. These reads report such a state; they prevent nothing.

Incident runbook: pause, enforce, resume

The order for an incident on one token: stop it, move what must be moved, resume. A quarantine account is an account prepared in advance to receive tokens taken from a holder.

  1. Pause. The guardian calls pause() on the token. Every movement except FORCED is rejected with PAUSED, the issuer's mint and burn included, and a vault's max* functions return 0. Calls that move no balance still work: setFrozenTokens, and the agent's setLockup and setFrozen. Each executor has its own pause(). Every entry point while paused.
  2. Enforce. The agent calls forcedTransfer(holder, quarantine, amount). It ignores the sender's credential, address freeze, lockup and minimum position, and may take frozen tokens, lowering the frozen amount by the part it takes. The receiver is still judged: quarantine needs an active credential the token's policy accepts (RECEIVER_NOT_VERIFIED, CREDENTIAL_EXPIRED, RECEIVER_NOT_ELIGIBLE) and must not be address-frozen (RECEIVER_FROZEN). On a fund class a forced move is exempt from the investor cap but still counted. On the 7540 vault, recoverRedeemRequest and recoverClaimable also work while paused. Several enforcement calls can go in one multicall.
  3. Resume. The token stays paused until unpause(), which only the main timelock or the recovery timelock can call, each after its delay. Plan for a pause of at least seven days. If the guardian cancels the unpause on the main timelock, governance uses the recovery path, which nobody can cancel.
  4. Burn what sits in quarantine. On IntentToken the burner calls burn(quarantine, amount) after the unpause. It is an enforcement burn, exempt from the lockup, the minimum position and the credential check on the sender, but quarantine must not be address-frozen.

Prepare the quarantine account before it is needed:

  • The KYC attester credentials it with the bits the token's policy asks for and renews it before it lapses: a lapsed account cannot receive, so a forced move into it would fail with CREDENTIAL_EXPIRED.
  • The agent never address-freezes it with setFrozen, because a frozen receiver refuses forced moves too. To keep it from sending, use setLockup: a lockup does not stop a forced move or the burner's burn. On a vault class its exit is its own redemption, which a lockup stops, so the agent clears the lockup first.
  • On a fund class, governance can exempt it from the investor count in advance with fund.setExempt(quarantine, true), a timelock operation that cannot wait for the incident.

A holder who is address-frozen cannot be emptied by burn, even the burner's (SENDER_FROZEN). forcedTransfer ignores the sender's freeze, so it is the way out of such an account, and the burn then comes from the quarantine account.

Why it is built this way

  • Two stages around the review. The hook's only immutable is the registry and it holds no rules until a token installs them, so its codehash depends on no token. The council can attest it, the rules and the implementations once, before any token exists, and every token is then created against attestations that already exist.
  • Install-time checks, not run-time ones. The registry is asked when a hook, a rule list, the fund's rule, a token or an upgrade is installed. Withdrawing an attestation later does not silently change a running token; governance removes the component, and the guardian can pause meanwhile.
  • Nothing granted until everything checks out. Calls wait for all three deploys and for the class registrations, so a mis-built token or rule list stops the deployment before any role exists.
  • Classes registered at zero supply. A token can join the fund only before it has any balance, and until it is registered its fund rule rejects every movement, so the fund has seen every holder there is.
  • A check after the hand-over. Attestation cannot tell two instances of the same code apart, and the rule lists live in the hook's storage, outside any codehash. The post-deploy check pins both.
  • Changes in one batch. Steps that would leave a token closed or uncounted in between, such as a hook swap and its lists, or a fund rule and its classes, go in one timelock batch, so no movement can fall between them.
